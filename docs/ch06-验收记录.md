### 验收 1：模型自己选工具、自己填参数（#1）

```console
$ POST /api/projects/1/chat  {"text":"这个会话里现在有多少条消息？只回答数字和单位。","sessionId":"real-s1"}
{"reply":"\"会话 real-s1 共有 5 条消息。\""}

$ select count(*) from chat_message where project_id=1 and session_id='real-s1';
6
```

数字差 1 不是 bug，是顺序：账本**先写「问」再调模型**，工具执行时账本里已经有本轮提问（5 条），
回答落账后变成 6 条。这条推断可以被下一轮证伪，于是再问一次：

```console
$ POST /api/projects/1/chat  {"text":"…有多少条消息？","sessionId":"real-s1"}
{"reply":"\"会话 real-s1 共有 7 条消息。\""}     ← 预测值 7（库里 6 + 本轮提问），命中

$ select count(*) ...;   →  8                      ← 答完又 +1
```

`returnDirect=true` 也在这里被证实：回答就是工具的原始返回值（连引号都是），
模型没有机会对这个数字做二次加工。

## 三、核验发现与踩坑

1. **工具执行循环在 ChatModel 实现内部，不在 ChatClient 里。**
   用假 ChatModel 测「模型发起工具调用」会得到假结论（我第一版就写了个永远不成立的单测）。
   正确分工：自己拥有的部分单测，模型的选择能力靠真实端到端验证。
2. **`.tools()` 只接受带 `@Tool` 注解的对象**；传 `ToolCallback` 实例必须用 `.toolCallbacks()`，
   否则报 `No @Tool annotated methods found`。
3. **匿名身份不能用 `-1L` 占位**：这样写出来的待确认记录 owner 是假的，人类确认时会被判「不属于该账号」。
   正确做法是「缺失就是缺失」，并在请求侧要求写能力带登录身份。
4. **统计类工具会把「本轮提问」算进去**（账本先写问再调模型），跨轮次看数字每次 +2。
   这是顺序决定的，不是错误；已写进本节与设计文档，避免后人当成 bug 去「修」。

## 四、本掌遗留问题

- **`REJECTED` 审计态还没有真实产生过**：目前应用层拒绝走的是工具自身返回值（`OK` + 拒因文本），
  真正需要「应用层直接拒掉、连工具都不执行」的场景（额度、越权）留到权限章节。
- **审计表没有归档与分页**：量大之后需要按时间分区或滚动归档。
- **工具结果没有进账本**：产品历史里只存了用户问题与最终回答，中间调了什么工具要靠审计表关联（第 17 掌）。
- **没有幂等键**：写工具靠确认令牌保证单次生效，但重复的「提议」会产生多条 pending。
- **超时值写死在配置**：不同工具应有不同上限（查库 200ms、调外部 API 3s），当前是全局一刀切。
