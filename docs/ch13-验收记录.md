## 二、真实环境验收（原始产物在 `scripts/evidence-ch13/`）

### 验收 1：两个独立进程，主服务不依赖对方的类

两个 jar 各自启动，各自报出自己的能力声明（`card-8082.json` / `card-8083.json`）：

```console
$ curl http://127.0.0.1:8082/.well-known/agent.json
{"name":"knowledge-agent","version":"1.0","url":"http://127.0.0.1:8082",
 "skills":[{"id":"knowledge-qa","name":"项目知识问答",...}],
 "capabilities":{"streaming":true,"taskLifecycle":true}}
```

主服务侧只有一份**协议副本**（`digital-human/a2a/A2AProtocol.java`），没有对方的任何类；
两份常量靠测试保证不漂移。

### 验收 2：多实例被分散调用（可观察）

```console
[实例列表] {"instances":[{"instanceId":"8082",...},{"instanceId":"8083",...}],"count":2}
[调用 1] instance=8082 task=task-5-f5fe764e7546 trace=f5fe764e7546 deltas=1 elapsedMs=8496
[调用 2] instance=8083 task=task-1-ec051ecc9307 trace=ec051ecc9307 deltas=1 elapsedMs=2274
[调用 3] instance=8082 task=task-6-109ede156ccd trace=109ede156ccd deltas=1 elapsedMs=1242
[调用 4] instance=8083 task=task-2-bc1ebc8ea7ff trace=bc1ebc8ea7ff deltas=1 elapsedMs=928
```

两件事同时被证明：**流量确实被分散**（8082 → 8083 → 8082 → 8083），
而且两边的任务号各自从 1 开始（`task-1/task-2` 在 8083、`task-5/task-6` 在 8082）——
**它们真的是两个独立进程、各自有状态**，不是一个进程装两个端口。

答案也来自各自的库：8082 只灌了「展厅手册」，8083 只灌了「产品手册」，
问展厅开放时间时命中来自 8082。

### 验收 3：贯穿标识与确定的失败语义

同一条 traceId 在两份日志里对上（`trace-correlation.txt`）：

```console
# 主服务
a2a.A2AClient : [a2a] trace=ec051ecc9307 instance=8083 task=task-1-ec051ecc9307 已创建
a2a.A2AClient : [a2a] trace=ec051ecc9307 instance=8083 task=task-1-ec051ecc9307 deltas=1 elapsedMs=2274

# 知识 Agent（ka-2 / 8083）
A2AAgentController : [a2a] trace=ec051ecc9307 task=task-1-ec051ecc9307 instance=ka-2 收到任务：展厅的开放时间是什么？
A2AAgentController : [a2a] trace=ec051ecc9307 task=task-1-ec051ecc9307 instance=ka-2 hits=2
A2AAgentController : [a2a] trace=ec051ecc9307 task=task-1-ec051ecc9307 instance=ka-2 completed answerLength=27
```

失败语义是**确定的**，不是随机的：4xx（版本/参数）不重试；
只有「对方可能没收到」的网络/5xx 才重试，且有次数上限与退避。

### 验收 4：版本不兼容 → 显式、快速、可诊断

```console
$ curl -X POST http://127.0.0.1:8082/a2a/tasks -H 'A2A-Version: 9.9' -d @q.json
HTTP 409
```

离线用例进一步断言「错误消息里同时含服务端版本与调用方版本」——
可诊断的要求是**看得出两边版本**，不是「状态码对」。

## 三、核验发现与踩坑

1. **文章点名的三个 starter 在 1.1.2.2 里不存在**（`-a2a-server` / `-a2a-client` / `-nacos-discovery`）。
   本掌按协议语义自己实现薄薄一层（能力声明 + 任务状态 + 流式 + 版本协商），
   Nacos 只作为发现实现之一接官方 `nacos-client`。
2. **`dependencyConvergence` 第四次拦住东西**：nacos-client → httpasyncclient → httpclient 4.5.13
   vs agent-framework 的 4.5.14。门禁的价值正在于这类分叉在单实例本地完全看不出来。
3. **YAML 列表绑不进 `@Value` 的 List**：第一次验收「实例列表」只有一个元素，
   表现为「永远只打第一个实例」，看起来像轮询没生效，实际是配置绑定问题。
4. **`${ENV:default}` 在变量存在但为空时给出空串**：boolean 绑定直接报
   `Invalid boolean value []`。默认值写在配置里，别指望环境变量总是「有值或没值」。
5. **Flyway 已应用的迁移不能再改**（这次是 V1 被 Windows CRLF 归一化改了内容）：
   开发库按 `flyway repair` 等价做法修复；工程结论是迁移文件一旦应用就当只读。

## 四、本掌遗留问题

- **本环境没有起 Nacos**：多实例分散调用用静态表验证，两条路径同一个 `AgentRegistry` 接口；
  Nacos 分支代码与开关都在，但**没有真实注册/订阅的落地证据**，不假装跑过。
- **任务表在内存里**：知识 Agent 重启即丢任务，悬挂任务无人清理（需要 TTL 或落库）。
- **流式只做了「服务端分片下发」**：首字延迟受对端 LLM 影响，真正的增量推理还没接。
- **没有契约版本化策略**：现在只有「版本不等就拒」，没有灰度与向后兼容协商。
