# 第 14 掌 · 损则有孚 · 溯源源码：把结论钉在 tag 上

> 对应文章：<https://cloud.tencent.com/developer/article/2752091>
> 分支：`chapter/14-source-pr` ｜ 标签：`ch14`

## 一、这一掌要解决的问题

前十三掌的判断都建立在「我读到的行为是这样」之上。问题是这句话没有主语：
**凭据是哪一份源码？** main 是开发中的事实，tag 是发布出去的事实；
本地跑起来的字节码由依赖坐标决定，由不得你打开的是哪个分支。

所以这一掌不加功能，只补工程能力里最容易被跳过的一环：**源码定位与开源协作**。
标准是把结论钉到「模块 → 类 → 方法 → 调用者 → 测试」，每一项都有真实文件与行号。

## 二、四条完成标准

| # | 标准 | 本掌怎么落 | 证据 |
|---|------|-----------|------|
| 1 | 锁定版本上给出「模块 → 类 → 方法 → 调用者 → 测试」完整链路，每项都有真实文件与行号 | 从 Maven Central 下 `*-sources.jar`（发布产物对应的源码），用 `scripts/locate-source.ps1` 复算行号 | `scripts/evidence-ch14/01~03`、`06` |
| 2 | 用 Git 历史说明行为何时引入、是否在版本之间变更过 | GitHub API 查该文件在 `v1.1.2.2` 之前的提交历史；并把 tag 版本与 main 逐行比对 | `04`、`05`、`07` |
| 3 | 产出最小复现，写成符合仓库模板的 Issue 正文 | 4 个断言的最小复现（离线、秒级）；Issue 草稿按上游 `bug_report.yml` 字段撰写 | `08`、`docs/ch14-上游Issue草稿.md` |
| 4 | 所有结论只追溯主仓一个事实源 | 事实优先级：官方文档 → 主仓源码与测试 → Release/CHANGELOG → 博客；生态仓库只作线索，且分别核验状态 | 本文件第一节与第四节 |

## 三、模块地图与本次链路

锁定版本：**Spring AI Alibaba 1.1.2.2 / Spring AI 1.1.2**（与 `pom.xml` 的 BOM 一致）。
源码来源：Maven Central 的 `-sources.jar`（不是 main，也不是「我本地的 IDE 缓存」）。

```text
行为：Agent 里工具调用失败时，框架的重试拦截器到底会不会重试？

模块  spring-ai-alibaba-agent-framework@1.1.2.2
  └─ 类    ToolRetryInterceptor
       └─ 方法  interceptToolCall          → ToolRetryInterceptor.java:75
            └─ 循环体 while (attempt <= maxRetries) → :86
                 ├─ try  return handler.call(request);   → :88   ← 关键：成功路径
                 └─ catch (Exception e)                  → :90   ← 关键：只有异常才进重试
  └─ 类    ToolErrorInterceptor（同版本自带）
       └─ 方法  interceptToolCall → ToolErrorInterceptor.java:26
            └─ catch (Exception e) → 返回 "Tool failed: …" 的正常响应 → :29-31
  └─ 调用者 InterceptorChain#chainToolInterceptors → InterceptorChain.java:72
       └─ 组装顺序：for (i = size-1; i >= 0; i--) → :85
            └─ 「**先声明的拦截器在最外层**」→ 注释 :84
  └─ 运行期调用者 AgentToolNode#executeToolCallWithInterceptors → AgentToolNode.java:230
       （串行：:218；并行：:290）
```

**结论（一句话）**：`ToolRetryInterceptor` 只对**抛异常**重试；
如果它内层有一个「把异常转成消息」的拦截器（框架自带的 `ToolErrorInterceptor`，
或我们第 9 掌的审计包装），重试就永远不触发——因为外层看到的是**正常返回**。

## 四、Git 历史：这个行为是怎么来的、变过没有

```console
# ToolRetryInterceptor.java 在 v1.1.2.2 之前的提交历史（GitHub API）
026799c5  2025-10-23  feat(agent): Add hook mechanism and implementations (#2641)   ← 引入
108415c7  2025-10-24  feat(agent): Interceptor opt, unit tests and bugfixes. (#2645)
8289920a  2025-11-16  Fix[model]: deepseek and openai serialization support for agent mode. (#3056)
c9414cb0  2026-01-01  fix: update license (#3972)

# ToolErrorInterceptor.java
1a3df556  2025-10-27  feat[agent]: Agent memory config and interceptor enhance. (#2656)  ← 4 天后引入
c9414cb0  2026-01-01  fix: update license (#3972)
```

也就是说：**「把异常转成消息」的拦截器比「重试」晚 4 天进主仓**，
而它一进来就与重试形成了顺序依赖——这个契约当时没有写在任何注释里。

再看 tag 与 main 的差异（`scripts/evidence-ch14/07-tag-vs-main-diff.txt`）：

```diff
- while (attempt <= maxRetries) {                     // 1.1.2.2：只重试「抛异常」
+ for (int attempt = 0; attempt < maxAttempts; attempt++) {
+     ToolCallResponse response = handler.call(request);
+     if (ToolCallResponse.SUCCESS_STATUS.equals(response.getStatus())) {
+         return response;
+     }
+     // A non-success status is treated as a failure so it can be retried.
+     String result = response.getResult() != null ? response.getResult() : "unknown error";
+     throw new RuntimeException(result);
```

**上游在 main 上已经改成了「非成功响应也当失败去重试」，还把 `maxRetries` 换成了 `maxAttempts`。**
我们锁的 1.1.2.2 没有这个修改——这正是「结论必须钉在 tag 上」的活例子：
同一段代码，在 main 上读和在我们跑的字节码上读，得到的答案不一样。

对我们工程决策的影响：第 9 掌把重试与兜底收回工具边界（自己实现）是**与上游方向一致**的；
将来升级依赖时，`ToolRetrySemanticsTest` 里那条「不重试」的断言会失败——这是**故意的路标**。

## 五、最小复现（离线、秒级、无模型）

`digital-human/src/test/java/com/example/digitalhuman/source/ToolRetrySemanticsTest.java`

| 场景 | 期望 | 说明 |
|------|------|------|
| `[error, retry]`（error 在外、retry 在内） | 调用 **3** 次 | 重试能看到异常 |
| `[retry, error]`（retry 在外、error 在内） | 调用 **1** 次 | 重试成了摆设 ← 我们踩过的坑 |
| 工具「只返回失败响应、不抛异常」 | 调用 **1** 次 | 1.1.2.2 的行为；main 上会变成 3 |

复现不需要模型、不需要数据库、不需要网络（3 秒内跑完）。

## 六、协作流程（怎么把这件事提交出去）

1. **事实源先对齐**：Issue 里必须写清版本（坐标 + tag），否则维护者复现不了。
2. **最小复现**：能贴成一段可运行代码或一个测试类；不要贴业务代码片段。
3. **Issue 按模板**：上游 `.github/ISSUE_TEMPLATE/bug_report.yml` 的字段——
   description / environment / expected / actual / steps to reproduce（草稿见 `docs/ch14-上游Issue草稿.md`）。
4. **文档类改动的提交信息**按本掌约定：`docs(ch14): map source modules and contribution workflow`。
5. **生态仓库分别核验**：主仓（spring-ai-alibaba）、Extensions、Examples 的状态各自确认，
   不把 A 仓的结论当成 B 仓的事实。

## 七、代价与适用条件（如实写）

- **时间成本前置**：第一次拉源码、解包、写定位脚本要小半天（本掌已把脚本落地，下次是一条命令）；
- **认知成本**：要同时看懂源码语义与构建结构，而不是只读一个类；
- **最容易被忽视的代价**：**版本升级会推翻既有结论**——所以定位脚本里版本号是显式常量，
  升级依赖时它会跟着改，而行号断言会在测试里失败报警；
- **适用条件**：问题得能描述成「可观察的行为」，并且该版本有源码与测试；否则定位退化为猜测。
