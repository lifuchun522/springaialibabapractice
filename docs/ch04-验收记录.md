### 真实错误映射

```console
# 目录外的模型名 → 400，并且直接告诉你有哪些可用
$ curl -X PUT .../api/projects/1/agent -d '{"provider":"deepseek","model":"gpt-9-不存在"}'
{"type":"MODEL_NOT_CONFIGURED","error":"模型不在目录中：deepseek/gpt-9-不存在，可用：deepseek/deepseek-flash、deepseek/deepseek-v4-pro"}
__HTTP__400

# maxTokens=16 逼出真实的「200 但内容为空」
$ curl -X POST .../api/projects/1/chat -d '{"text":"用一句话介绍你自己"}'
{"error":"模型返回了空内容（HTTP 成功但没有有效回复）","type":"MODEL_EMPTY_RESPONSE",
 "provider":"deepseek","model":"deepseek-v4-pro"}
__HTTP__502

# 恢复参数后接口正常
$ curl -X POST .../api/projects/1/chat -d '{"text":"用一句话介绍你自己"}'
{"reply":"我是深圳展厅的数字人讲解员，专门带您逛深圳、讲深圳故事。"}
__HTTP__200
```

最后一条是这一掌最有价值的真实证据：**上游 HTTP 200、内容为空**这种失败，
如果没有显式判定，运行页上就只会看到一片空白，而日志里全是「成功」。

## 四、本掌遗留问题

- `TIMEOUT` / `UNAVAILABLE` 两类只有单测覆盖（用一个假的 ChatModel 抛出对应异常），
  没有做「真实断网/真实限流」的端到端演练——那需要可复现的故障注入手段，留到生产化章节。
- 只有一条 provider 通道，第二家 provider 的接入没有真实跑过（文章里的双 provider 演示在本仓库尚未具备条件）。
- `topP`、`stop`、结构化输出等参数未接入；流式（`stream()`）按文章口径留到下一掌。
- 会话记忆仍不存在：每次调用都是无状态的一问一答（第 5 掌）。
