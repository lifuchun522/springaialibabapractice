### 验收线 1：记忆生效且不串线（真实模型）

```console
# 第 1 轮：同一 sessionId=real-s1
$ POST /api/projects/1/chat  {"text":"我叫小明，请记住这个名字。","sessionId":"real-s1"}
{"reply":"好嘞小明，记住啦！欢迎来深圳展厅找我，带你逛深圳～"}

# 第 2 轮：同一会话，问名字
$ POST /api/projects/1/chat  {"text":"我叫什么名字？只回答名字。","sessionId":"real-s1"}
{"reply":"小明"}          ← 记忆真的进了上下文

# 第 3 轮：换 sessionId=real-s2，问同一句
$ POST /api/projects/1/chat  {"text":"我叫什么名字？只回答名字。","sessionId":"real-s2"}
{"reply":"不知道"}        ← 不串线
```

这三行是本掌最有说服力的证据：**同一个问题，只因为 sessionId 不同，答案从「小明」变成「不知道」**。

### 验收线 2：SSE 增量（真实模型）

```console
$ curl -N "http://localhost:8080/api/projects/1/chat/stream?sessionId=real-s4&text=用一句话说说深圳的海"
data:深圳
data:的海
data:啊
data:，
…（共 32 帧）

HTTP/1.1 200
Content-Type: text/event-stream
Transfer-Encoding: chunked
__HTTP__200 首字节=8.791700s 总耗时=9.235535s
```

如实记录一个不那么好看的数字：**首字节 8.8 秒**。流式降低的是「首字节之后的体感等待」，
它不解决首字节本身——对带推理阶段的模型，这段延迟来自模型，不来自传输层。
把这条写进记录，是为了避免用「上了流式就好了」这种结论掩盖问题。

## 三、核验发现与踩坑

1. **MockMvc 默认按 ISO-8859-1 读响应**，SSE 里的中文会变乱码导致断言假失败；
   必须 `getContentAsString(StandardCharsets.UTF_8)`。SSE 按规范就是 UTF-8。
2. **EventSource 会自动重连**：服务端流结束后浏览器会再发一次同样的请求（把同一句话问两遍）。
   前端改用 `fetch` + `ReadableStream` 自行解析 `data:` 帧。
3. **JUnit 每个用例新建测试实例**：把注册/建项目放在 `@BeforeEach` 会重复注册同名用户直接报错；
   一次性初始化要放 `@BeforeAll` + `@TestInstance(PER_CLASS)`。
4. **管道截断会真的触发取消**：`curl … | Select-Object -First 30` 会在读满后关掉管道，
   服务端随即看到客户端断开——这既是排查时的干扰项，也正好验证了取消路径确实生效。

## 四、本掌遗留问题

- **落库在响应式回调里是阻塞的**（JPA）：语义正确但不是最终形态，生产化要换异步写入或 R2DBC。
- **Memory 仍是内存态**：多实例部署会各记各的、重启即丢；换 `ChatMemoryRepository` 为 JDBC/Redis
  即可，但选型与压测没做。
- **没有断线续传**：SSE 事件没有 ID 与游标，客户端重连只能重问。
- **没有 token 预算策略**：窗口按条数（20 条）而不是按 token 裁剪。
- **没有观测指标**：取消率、首字节耗时、超时率目前只能靠日志（第 17 掌）。
- **超时未显式设置**：上游慢到多久算超时、超时后账本怎么记，尚未定义（第 18 掌前的生产化课题）。
