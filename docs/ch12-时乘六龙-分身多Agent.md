## 一、这一掌要解决的问题

到第 11 掌为止，数字人已经有一套状态图在管流程。但**每个角色自己的上下文**还是糊的：
接待话术、文档片段、查询参数共用一份 System Prompt 与一份记忆，工具清单越来越长。

具体代价是三笔账：

- **上下文预算**：一次调用的上下文 = 系统提示词 + 全部工具的名称与 Schema + 历史消息 + 检索片段 + 本轮输入。
  工具从 4 个涨到 12 个、提示词随职责线性变长——**这些钱每轮都要付，且与问题是否相关无关**；
- **记忆污染**：接待轮的寒暄、知识轮的片段、业务轮的参数混在一份历史里，下一轮看到的是一锅粥；
- **修改不局部**：改一条职责的提示词，要回归另外两条职责。

## 二、三条完成标准

| # | 标准 | 本掌怎么落 |
|---|------|-----------|
| 1 | 三个角色在同一张链路里协作，一次会话内可以流转 | Router 定第一跳 → 角色在回复末尾输出 `handoff=<role>` → Supervisor 握着 `max-hops` 上界 |
| 2 | 每个角色只带自己的提示词、工具与记忆 | 工具归属写死在 `MultiAgentRoles`（任何两个角色不共享工具）；记忆按 `role:sessionId` 命名空间各一份 |
| 3 | 能一句话解释「为什么必须多 Agent，而不是一个 Agent 加更多 Tools」 | 判据写在下面第四节 |

## 三、控制权的三层划分

```text
Router（第一跳，一次分类，固定温度）
    → 角色（自己决定要不要交接：回复末尾 handoff=<role>）
        → Supervisor（还要不要继续跳：max-hops 硬上界，跳过的角色不再回跳）
```

三种控制权模式的差别不在 API，而在**谁决定下一个动作 + 谁能看到哪些状态**：

| 模式 | 谁决定 | 状态边界 | 本掌用法 |
|------|--------|----------|----------|
| Routing | 前置逻辑 | 天然隔离，每个分支一份干净上下文 | 第一跳用 Router |
| Supervisor | 中心 Agent | 默认共享 | 用 `max-hops` 收敛，避免无限跳 |
| Handoff | 当前角色自己 | 只带该带的那部分 | 角色输出 `handoff=`，交接后自己停下 |

## 四、判据：什么时候才轮到多 Agent

一次调用塞进上下文的五项之和就是**上下文预算**。工具与提示词是固定成本，**与这一轮问题是否相关无关**。

所以判据只有一条：**当不同职责对「提示词 / 工具集 / 记忆」的要求互相排斥时，才轮到多 Agent。**

- 只是工具变多 → 加工具就够了，拆角色只是多付几次模型调用；
- 一套人格装不下（接待要热情、知识要严谨、业务只报事实）→ 才该拆；
- 拆完必须能验证两条硬边界（工具不共享、记忆不污染），否则等于没拆。

**反直觉的地方**：拆多 Agent 的第一收益不是能力更强，而是**上下文更窄**。
能力上限没提高，是候选空间变小让误选概率下降了。

## 五、取舍与代价

- **延迟变高**：一次会话可能产生多次模型调用（本掌实测：一次流转 = 分类 1 次 + 角色 2 次）；
- **Router 误判会让整条链路从一开始就跑偏**——本掌的真实运行里就出现了一次
  （「团体讲解提前几天」被判给了业务角色），好在那条链路**守住了边界**：
  业务角色明确回答「我这边没有这个口径或数据，不能凭猜测回答」，而不是硬答；
- **图状态成了新的共享可变区**：少写一个 key 策略就会覆盖（第 11 掌的教训直接适用）；
- **记忆目前是进程内的**：与第 5 掌的账本不同，这里的三份记忆是 `MessageWindowChatMemory`，
  进程重启即空。跨重启的角色记忆要接同样的持久化思路（遗留问题）。
