# 第 7 掌 · 突如其来 · 通玄 MCP：把能力交出去，把错误分清楚

> 对应文章：<https://cloud.tencent.com/developer/article/2752101>
> 分支：`chapter/07-mcp` ｜ 标签：`ch07`

## 一、这一掌要解决的问题

第 6 掌的工具是**进程内**的：写个方法、加个注解，调用方就是自己，参数校验靠编译器。
本掌换了前提——「展厅预约」这份能力的**归属**变了：

- 它的数据不在数字人库里（`digital_human_ext.showroom_booking` 只存在于 Server 侧）；
- 调用方不止一个（数字人运行页、以后的实时语音 Bridge、其它产品线）；
- 数字人这边不再拥有那段逻辑，只能成为一个调用方。

一旦跨进程，「参数校验」从编译期退化到运行期（模型决定传什么），
「错误」也从一种变成三种。所以这一掌真正标准化的是**错误**，不是调用。

## 二、拆与不拆的判据：看调用方有几个

文章里那条判断值得原样抄下来：**一个能力该不该拆成 MCP Server，看它有几个调用方，而不是看它复不复杂。**

- 只有一个调用方的复杂能力，拆出去只换来「多一个进程、多一条部署依赖、多一类故障」；
- 有第二个真实调用方（或调用方是别的语言）时，拆才开始有正收益。

本仓库照这个判据落了两套东西，待遇不同：

| 能力 | 归属 | 传输 | 为什么 |
|------|------|------|--------|
| 项目信息、会话统计、标题变更 | 数字人自己 | 本地 `@Tool`（同进程） | 只有自己用，确定性逻辑 |
| **展厅预约** | **独立 MCP Server**（`digital-human-mcp` 模块，端口 8081） | MCP over Streamable HTTP | 数据不属于我们，且调用方会变多 |

`digital-human-mcp` 是一个**独立 Maven 模块、独立进程、独立数据库**（`digital_human_ext`）。
数字人服务想拿预约数据，只有协议这一条路——这不是设计洁癖，是让「归属」这件事物证化。

## 三、错误必须分层，否则协议成本白付

MCP 把三类情况在协议层分开表达，本掌逐条落：

| 层 | 情况 | 本掌的表现 |
|----|------|-----------|
| 传输层 | Server 不可达 / 路径协议不匹配 | 客户端初始化失败，启动直接失败并带出 URL 与状态码 |
| 协议层 | 工具不存在、参数不符合 Schema | JSON-RPC 错误响应（框架层处理） |
| **业务层** | 展厅当天没排期、日期格式错 | **调用成功**，内容里带 `{code, message}`：`NO_SLOT_AVAILABLE` / `INVALID_ARGUMENT` |

业务错误刻意**不用异常抛**：异常只有「失败」一种语义，而业务错误需要调用方**分得清**。
所以 `showroom_query_availability` 成功与业务失败返回同一个结构（`status=OK/ERROR` + `error.code`），
调用方据此写确定的分支，而不是 catch 一个 Java 异常再猜。

## 四、发现机制：不许静默为空

MCP Client 连不上 Server 时，最容易出现的坏结果是「一个工具都没有，但启动成功」——
运行期表现是「模型忽然不会查预约了」，而日志里什么都没有。

所以本掌在启动后主动拉一次清单（`McpDiscoveryCheck`）：

```text
MCP 远程工具已发现 1 个：showroom_query_availability
```

清单为空时按 `digital-human.mcp.fail-fast`（默认 **true**）直接启动失败，并把常见原因写进消息里。
测试环境（`application-test.yml`）关掉它，因为单测不该依赖外部进程。

## 五、与文章的差异（如实记录，这条比较重要）

文章第 06 节第一条排查链说：客户端端点与 Server 协议不匹配（例如客户端配 `/sse`、Server 是 `STREAMABLE`）
时，「不会报协议不匹配，只会得到 404，然后被客户端静默处理成没有工具」。

**这条在本仓库的技术栈上没有复现。** 实测（Spring AI 1.1.2 + mcp-spring-webflux 0.17.0）：

```text
io.modelcontextprotocol.spec.McpTransportException: Sending request failed,
    404 Not Found from GET http://localhost:8081/sse
io.modelcontextprotocol.spec.McpTransportException: Sending request failed,
    404 Not Found from POST http://localhost:8081/sse
→ 应用启动失败（不是静默无工具）
```

也就是说：这一版客户端**把 404 与 URL 都明确抛了出来**，比文章描述的更友好。
我们的 `McpDiscoveryCheck` 仍然是必要的——它守的是另一种情况：
客户端初始化成功、但 Server 的工具清单确实为空（例如 Server 侧没注册工具）。
两种情况的表现不同，处置也不同，这一点写清楚，免得后人照文章去查一个不存在的现象。

## 六、四类故障的完整表现（本掌的验收核心）

| 故障 | 表现 | 谁负责 |
|------|------|--------|
| 端点端口不通 | 启动失败，堆栈里是连接层异常（`ClosedChannelException`） | MCP 客户端 |
| 路径/协议不匹配（404） | 启动失败，异常里带 URL 与 404 | MCP 客户端 |
| Server 运行中断连 | **启动不失败**；调用时工具失败 → 审计 `ERROR` → 模型优雅降级为「稍后再问」 | 我们的装饰器 + 模型 |
| 业务上「这天没排期」 | 调用成功，内容里带业务码 `NO_SLOT_AVAILABLE` | Server 侧设计 |

第三类最值得说：**Server 重启的两分钟里，用户看到的不是报错页，而是一句人话**；
Server 回来后，同一个数字人进程**不需要重启**就能继续查询（实测已验证）。

## 七、运维视角（写清楚代价）

拆出去的代价是三条：多一跳网络、多一个要独立监控与发布的进程、工具描述成了新的故障源
（描述写错=接口写错，因为远程调用方只读得到描述）。收益是三条：调用方不需要我们的 SDK、
能力只维护一份、错误职责清晰（数据类问题归 Server，编排类问题归数字人）。

下一掌（第 8 掌 RAG）会继续用这个边界，第 13 掌再叠加注册中心做动态发现——
到时把地址从配置项换成 `Nacos`，本掌的客户端与工具都不需要改。
