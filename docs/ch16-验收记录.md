## 3. 缺配置时到底发生什么

```text
$ java -jar digital-human.jar --server.port=8091        # 故意不带 DEEPSEEK_API_KEY
ERROR ... o.s.boot.SpringApplication : Application run failed
java.lang.IllegalStateException: 部署契约不满足：缺少必需配置 spring.ai.openai.api-key
（环境变量 DEEPSEEK_API_KEY）……这一项没有安全默认值——给占位值只会把启动期错误
推迟成第一次请求的失败。请在部署清单里声明它（deploy/.env、K8s Secret 或 docker run -e）。
```

三点值得记下来：

1. **失败发生在启动期**，不是第一次请求（文章 06 链 A 的现象在本仓库被前移掉了）；
2. **错误信息归我们所有**：Spring AI 自己也会因为空密钥抛 `OpenAI API key must be set`，
   但那条信息不会告诉你「缺的是哪个环境变量、去哪儿声明」。校验位置放在
   `ApplicationContextInitializer`（Bean 创建之前）才拿得到这个信息所有权；
3. 健康检查与启动校验读**同一份清单**（`DeploymentContract`），不会出现「启动期必需、健康检查可选」的漂移。

## 4. 健康检查：分组切对了才有意义

```json
// 03-health-liveness.json —— 只回答「进程还在不在」
{"status":"UP","components":{"ping":{"status":"UP"}}}

// 03-health-readiness.json —— 回答「现在能不能接流量」
{"status":"UP","components":{
  "configReadiness":{"status":"UP","details":{
     "spring.ai.openai.api-key":"present",
     "digital-human.chat.default-system":"present",
     "digital-human.a2a.instances":"set",
     "digital-human.a2a.nacos.server-addr":"set",
     "spring.ai.mcp.client.streamable-http.connections.showroom.url":"set"}},
  "db":{"status":"UP","details":{"database":"MySQL","validationQuery":"isValid()"}},
  "diskSpace":{"status":"UP"}}}
```

`liveness` 刻意只含 `ping`：把配置或数据库放进去，配置一缺、库一抖，K8s 就会把还活着的进程
反复杀掉重启，把「配置问题」放大成「服务雪崩」。

## 6. 真实验收抓到的三个问题

### 6.1 空流被记成「正常答完」（已修）

**现象**：压测长回答时撞上一次——服务端 200、连接正常关闭、前端什么都没收到；
账本里那条助手消息是 `COMPLETED`、内容长度 0。

```
$ curl -N ".../chat/stream?text=请逐段写一篇不少于 600 字的自我介绍&sessionId=ch16-long"
（只有 :heartbeat，没有任何 data 帧，然后正常结束）

mysql> select session_id, role, status, char_length(content) from chat_message where session_id='ch16-long';
ch16-long  USER       COMPLETED  59
ch16-long  ASSISTANT  COMPLETED   0     ← 空回答被记成成功
```

同一次对话换阻塞式接口（`05-blocking-answer.json`）返回 553 字符正常答案；
同一 prompt 换新会话重跑两次都正常（**间歇性**，不是必现）——所以它不会被一次两次手测发现，
只会作为「前端偶尔什么都不显示」被投诉上来。

**根因**：阻塞式路径有「200 但内容为空 → `EMPTY_RESPONSE` 显式失败」的守卫，流式路径没有。
同一个语义在两条契约上表现不同，就是交付契约没对齐。

**修法**：流式路径补 `switchIfEmpty` 抛 `EMPTY_RESPONSE`，账本记 `FAILED` 并写明原因；
断言见 `service/EmptyStreamContractTest`（同时钉住「失败后会话锁必须释放」）。

### 6.2 默认异步执行器不适合生产负载（已修）

**现象**（首次带心跳的真实流式请求，21:35:07）：

```text
WARN o.s.w.s.m.m.a.RequestMappingHandlerAdapter :
Performing asynchronous handling through the default Spring MVC SimpleAsyncTaskExecutor.
This executor is not suitable for production use under load.
```

**为什么单测挡不住**：功能全对，只在负载下出问题——每请求新建线程、没有上限、没有队列。
这正是「Demo 能跑、交付不能」。

**修法**：`config/WebAsyncConfig` 配上有界线程池（core 4 / max 32 / queue 200）、显式 5 分钟超时、
优雅停机；断言见 `config/WebAsyncConfigTest`。修复后同一条真实链路不再打印该警告
（修复后的完整日志：`02-app-run.log`，可用 `Select-String 'SimpleAsyncTaskExecutor'` 复核，无命中）。

### 6.3 部署清单没有声明必需项（已修）

`deploy/docker-compose.yml` 原来直接写 `${APP_DEEPSEEK_API_KEY}`——没设就是空字符串，
缺失被带进容器，变成第一次请求的 401。现在必需项写成 `${VAR:?提示}`：

```text
$ docker compose -f docker-compose.yml config      # 不设 APP_DB_URL / APP_DEEPSEEK_API_KEY
error while interpolating services.digital-human.environment.DIGITAL_HUMAN_DB_URL:
required variable APP_DB_URL is missing a value: 缺少 APP_DB_URL：数据库地址必须由部署环境声明（deploy/.env 或 K8s ConfigMap）
```

同时把容器探针从 `/actuator/health` 改成 `/actuator/health/readiness`——
前者只说明「进程活着 + 依赖没挂」，后者含 `configReadiness`。

## 7. 依赖方向门禁第一次跑就抓到真实违规

```
arch/LayeredArchitectureTest.apiMustNotTouchPersistence  ← 第一次运行：violated (3 times)
  Constructor <com.example.digitalhuman.web.ToolController.<init>(..., ToolCallAuditRepository)>
  Method <com.example.digitalhuman.web.ToolController.toolAudits(...)>
      calls method <ToolCallAuditRepository.findByProjectIdOrderByIdDesc(Long)>
```

`ToolController` 自己注入 repository 查库：跑得通，但把「谁能读、读哪个项目的、怎么读」
混进了 HTTP 层。修法是新增 `service/ToolAuditService`（授权 + 查询合成一个用例），
依赖方向变回 `web → service → repository`；6 条 ArchUnit 规则现在全绿。

同一轮还暴露了我自己写的规则**过宽**：`..web..` 会同时匹配 Spring 的
`org.springframework.web.reactive.function.client`，于是把 A2A 客户端里的 `WebClient`
误判成「业务层依赖 web 层」（23 处）。规则改成精确包名
`com.example.digitalhuman.web..` 之后才真正只盯我们自己的包——
**门禁也是代码，写宽了会红一片、写窄了会漏一片，两边都要用真实违规校一次**。
