# 第 15 掌 · 龙战于野（试炼评测）：五层测试与六类回归集

> 文章：[降SpringAI阿里第15掌-龙战于野-试炼评测](https://cloud.tencent.com/developer/article/2752089)
> 分支：`chapter/15-eval-guard` ｜ 证据：`scripts/evidence-ch15/`
> 一句话：**单测全绿，数字人却答非所问**——问题不在有没有测试，而在断言放在了哪一层。

## 1. 这一掌要修的到底是什么

前十四掌把能力攒齐了：ChatClient、Memory、Tool、MCP、RAG、ReactAgent、Flow、Graph、多 Agent、A2A。
仓库里也有 118 + 5 + 4 条离线用例，`./mvnw clean verify` 三十多秒就绿。但那种绿**证明不了链路行为**：

- 把 `ChatModel` mock 掉，被测行为就止步在 mock 那一层。System Prompt 怎么拼、工具定义有没有随请求发出、
  历史有没有回灌、召回片段有没有进上下文——全部发生在 mock 之外，一条都没被验证。
- 一旦把断言写在**模型输出**上（`assertThat(answer).isEqualTo("你好，我是财税小助手。")`），
  测试就变成了对随机文本的断言：同一个用例连跑三次，两次过、一次挂，挂的那次语义还是对的。
- 依赖外网的用例（A2A 跨域）在本地能过、在 CI 必挂，因为它需要本机 Nacos 和外网远端 Agent。

把这三件事翻译成一句工程判断：**确定性逻辑必须强断言，模型输出禁止用固定文本强断言**，
而断言应该尽可能前移到「我们发出的输入」和「模型必须走的分支」上——这两样都是确定的。

## 2. 五层落在本仓库的哪里

| 层 | 测什么 | 本仓库落点 | tag | 进 CI 阻断 |
| --- | --- | --- | --- | --- |
| L1 单元 | Prompt 拼装、参数解析、会话隔离、Graph 条件边、State 归约 | `digital-human/src/test/java/...`（118 条 + 本掌新增 15 条） | 无 | 是 |
| L2 组件 | 真实 ChatModel / Agent / 工具链路，**断言我们发出去的请求** | `component/ModelHttpStubComponentTest`（MockWebServer 打在 HTTP 层） | 无 | 是 |
| L3 集成 | 真实外部依赖：迁移、连接、映射 | `integration/FlywayMysqlIntegrationTest`（Testcontainers `mysql:8.0`） | `integration` | 否 |
| L4 离线回归评测 | 判据 + 数据集：真实输出快照重放、结论与基线对照 | `eval/RecordedRegressionReplayTest` + `regression/recorded/answers.json` | `eval` | 否 |
| L5 在线评测 | 真实模型跑六类回归集，产出可追溯记录 | `eval/LiveEvalRunTest` + `target/eval-runs/` | `eval-live` | 否 |

tag 隔离落在根 pom 的 Surefire 配置上，用属性而不是写死的值：

```bash
./mvnw -B -ntp clean verify                                                       # CI：L1 + L2
./mvnw -B -ntp verify -Dsurefire.groups=integration -Dsurefire.excludedGroups=    # L3
./mvnw -B -ntp verify -Dsurefire.groups=eval -Dsurefire.excludedGroups=           # L4
./mvnw -B -ntp verify -Dsurefire.groups=eval-live -Dsurefire.excludedGroups=      # L5
```

**为什么用属性而不是把 `excludedGroups` 写死在插件里**：写死之后，想跑一次集成测试就得改 pom 再改回来，
而这类「临时改动」迟早会被顺手提交。这里踩过一次真实的坑：Surefire 里 `excludedGroups` 与 `groups`
同时命中时**排除优先**，只写 `-Dgroups=integration` 会一条用例都跑不到，还显示成功——
所以两条命令必须成对出现，这一条写进 `scripts/evidence-ch15/README.md`。

## 3. 六类回归集与各自的断言策略

回归集的定义在 `digital-human/src/test/resources/regression/*.json`，六类各一个文件，带数据集版本号。

| 回归集 | 确定性部分（规则强断言） | 非确定性部分（Judge / 人工） | 本仓库落点 |
| --- | --- | --- | --- |
| 普通问答 `qa-basic` | 开场白、会话隔离、长度边界、不泄露他项目内容 | 回答措辞 | LIVE 3 条 + OFFLINE 1 条 |
| 项目知识 `project-knowledge` | **召回条数**、**是否走系统拒答分支**、必须带依据序号 | 引用是否自然 | LIVE 3 条 |
| 工具调用 `tool-calling` | **审计表里真实发生过的工具名**、工具定义随请求发出 | 是否需要调用 | LIVE 2 条 + OFFLINE 2 条 |
| Workflow `workflow` | 分类路由、补信息轮数上界、条件边与 State 归约 | 节点选择是否合理 | OFFLINE 3 条 |
| Multi-Agent `multi-agent` | 路由规则、Handoff 跳数上界、A2A 协议结构 | 分工是否恰当（人工抽样） | OFFLINE 4 条 |
| 安全拒绝 `security-refusal` | **禁止内容硬约束**、写工具门禁、Schema 无身份字段 | 拒答是否到位、越狱变体识别 | LIVE 4 条 + OFFLINE 2 条 |

两处设计选择值得单独说：

1. **凡是系统自己决定的事实，一律从运行侧记录取，不从回答文本里猜**。
   「模型有没有调工具」取的是 `tool_call_audit` 审计表；「依据有没有进上下文」取的是
   `RagAnswerService` 返回的 `sources` 条数；「走没走拒答分支」取的是它返回的 `refused` 标记。
   模型在回答里说「我调用了 getProjectInfo 工具」不算数——这条体现在
   `RuleEvaluatorTest.shouldAssertToolsFromAuditFacts` 里。
2. **判据匹配只在空白与大小写上宽容**（`8折` 与 `8 折` 视为同一件事），别的一律严格。
   这两个是排版差异、不是行为差异，把它们当失败会制造一批没人修的假红；而放宽语义则会让假绿复活。

具体条数与通过率**不预设**：本掌只放 12 条 LIVE 用例 + 6 条校准样本把机制跑通，
阈值取自校准结果，不取想象。这一点与文章一致（文章同样不给数字）。

## 4. 关键改动：把 mock 边界从 ChatModel 撤到 HTTP 层

`component/ModelHttpStubComponentTest` 是全掌最关键的一次改动，它断言的是**我们发出去的请求**：

- `request.getPath()` 必须是 `/v1/chat/completions`（证明真的走了配置的通道，没有偷偷打到外网）；
- 请求体里必须有 `"tools"`、`getProjectInfo`、`querySessionStats`（工具定义在不在）；
- 请求体里**不能出现 `projectId`**（身份只能走 ToolContext 旁路，模型看不见也填不了）；
- 请求体里必须有 System Prompt（`"role":"system"` + 默认人设原文）；
- 第二轮请求体里必须出现第一轮的问答（历史回灌），以及配置里的模型名 `deepseek-flash`。

这一层能抓到什么：故意注释掉工具注册代码，这里就会红，且失败信息直接指向「请求体缺少工具定义」——
**失败即可归因**，这是第 15 掌反复强调的那条标准。

边界也要写清楚：桩响应是「我们以为模型会返回的」，不是真实模型行为。所以 L2 只验证链路正确性，
**不验证效果好坏**。把两者混起来，会得到一批自信的假绿。

## 5. Judge 与校准

`eval/LlmJudge` + `eval/ChatClientLlmJudge`：温度固定 0、只认 JSON、判据由数据集逐条给出、
解析失败按「无法判定」处理（而不是猜一个分数）。`eval/JudgeCalibration` 用一小批人工标注样本
对照 Judge 判断，算**方向一致率**——校准不追求不差分毫，只要求人判通过的它也通过、
人判该拒答的它也不给分。

**这一层第一次真实运行就暴露了自己的缺陷**：报价用例的判据是「没有编造资料以外的折扣」，
但 Judge 只拿到判据和回答，看不到项目资料里本来就写着「满 20 台按 7.5 折」，
于是把一条完全正确的回答判成 0 分，理由写着「编造折扣」。
结论不是「调低阈值」，而是「**Judge 看不到事实，就会把事实当编造**」——
修法是把召回的资料原文一起给它（`LlmJudge.score(question, answer, criterion, reference)`）。
过程与证据见 `docs/ch15-验收记录.md`。

## 6. 与文章的差异（按本仓库基线核验后调整，不照抄）

| 文章 | 本仓库 | 原因 |
| --- | --- | --- |
| L2 桩 `spring.ai.dashscope.base-url` | 桩 `spring.ai.openai.base-url` | 本仓库只有一条模型通道：DeepSeek 走 OpenAI 兼容协议（第 2 掌的取舍）。照抄 dashscope 的属性名不会生效，请求会真的打到外网 |
| 工具名 `getProjectKnowledge` | `getProjectInfo` + `querySessionStats`，知识走 `RagAnswerService` | 本仓库的工具划分：项目信息走只读工具，知识走 RAG 服务（第 6/8 掌） |
| L3 容器 `pgvector/pgvector:pg16` | 容器 `mysql:8.0` | 本仓库真源是 MySQL + Flyway（`knowledge_document` 是真相，向量库是可重建投影）。跑在与线上不同的数据库上，只能验证「另一个库也能跑」 |
| L4/L5 由 `spring-ai-alibaba-admin` 承载 | Maven tag + 本地 runner，记录落 `target/eval-runs/` | 本仓库没有 Admin 侧评测模块。**这是遗留项**，不是等价替代：数据集管理、历史趋势、多任务对比都还没有 |
| `excludedGroups` 写死在 Surefire | 属性 `${surefire.excludedGroups}` | 让「按层触发」不用改 pom；同时避免「改完忘改回来」被提交 |
| 五层全部上 | L1/L2 做扎实，L3 只覆盖最关键的依赖，L4 从安全拒绝与工具调用先跑起来 | 文章自己也说：三人小团队硬上五层很可能维护不动。复杂是代价，不是勋章 |

## 7. 代价与适用边界

- **代价**：本地跑测试从三十多秒涨到几分钟（L1+L2）；L4/L5 还要人维护回归集与判据、定期校准 Judge。
- **收益**：任何一次 Prompt / 模型 / 拓扑 / 依赖的改动，都能回答「改了什么、影响了哪几类行为、有没有人复核过」。
- **不适用**：还在找产品形态的原型阶段。需求一周一变，回归集今天写完明天作废。
  它适合的是第 15 掌这个位置——业务范围已经固定成六类，框架能力在固定基线上增加。

## 8. 遗留问题（诚实清单）

1. Judge 的定期校准机制没有形成节奏：现在是「跑评测时顺手校准一次」，没有时间线。
2. Multi-Agent 的路径类用例仍以人工抽样为主，自动化程度最低（本掌只把确定性的路由与跳数上界钉住）。
3. A2A 跨域评测没有稳定的容器化方案，仍依赖外部环境，因此只保留协议层断言。
4. 无依据拒答分支的判据留在评测集里**持续失败**（详见验收记录第 4 节）：
   本地哈希嵌入下相似度阈值形同虚设，`refused` 分支在这种配置下几乎走不到。这是真实缺陷，未在本掌修复。
5. Admin 侧评测数据组织形态未对齐，L4/L5 的历史趋势还没有落库。
