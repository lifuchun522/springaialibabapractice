## 一、先说时机：2026 年这波 Java Agent 浪潮，热的不是模型，是框架

今年这一年，Java 生态里的 AI 框架发生了三件绕不开的事：

| 时间/事件 | 对我们的实际影响 |
| --- | --- |
| **Spring AI 2.0.0 GA 发布**（[官方公告](https://spring.io/blog/2026/06/12/spring-ai-2-0-0-GA-available-now)） | 基础抽象层进入正式版，Advisor、Tool Calling、MCP、RAG、Observability 全线稳定，Java 团队"接入 AI"的门槛基本消失 |
| **Spring AI Alibaba 1.0 GA + Agent Framework / Graph Runtime**（[官方博客](https://java2ai.com/blog/spring-ai-alibaba-1.0-ga-release/)、[GitHub](https://github.com/alibaba/spring-ai-alibaba)、[文档站](https://java2ai.com)） | Agent 层与图运行时补齐，"Java 只能写 CRUD 调模型"的刻板印象被打破 |
| **开源争鸣：AgentScope Java 2.0、各家 ADK 陆续入场** | 选型从"有没有得选"变成"选错了怎么返工"——**框架选型第一次成为架构决策，而不是依赖坐标** |

结论很直接：**这半年真正卡住 Java 团队的，不是"怎么把模型调通"，而是"调通之后怎么长出 Agent，并且不返工"。**

而网上的内容，绝大多数停在第一站。所以这套系列从**第一站之后的第二站**开始讲。

## 二、为什么大多数人卡在同一处：Demo 通，架构不通

如果你现在的代码长这样，这篇就是写给你的：

- System Prompt 拼在 Controller 的字符串里，运营改一句话要发一次版；
- 会话状态躺在一个 `ConcurrentHashMap`，两个浏览器同时打开就串线；
- 想加"查订单"就加一段 `if-else`，加完 RAG 再加一段，加完多 Agent 再 `role` 字段；
- 模型换供应商，改的是 `import` 语句，不是配置；
- 出问题只能看到最终那段文本，看不到走了哪个工具、检索到什么、哪一步走的哪条分支。

第 1 掌给这种现象起了一个名字，并且说明了它为什么会必然发生：**旧方案在"单轮问答"场景下是正确的，一旦需求跨过"有状态 / 多步 / 可中断 / 可观测"这条线，它失效的不是某一段代码，而是整条结构。**

同一个判断换个说法就是这篇系列的取舍原则：

> 选型即边界，边界即成本，成本即架构，架构即取舍。

## 三、"降"是什么意思：不是降级，是把框架压到可控

这个系列叫「降 Spring AI 阿里」，借的是**降龙十八掌**的骨架——18 掌，一掌一个动作，掌掌有内功、有外功、有可验证的完成标准。

"降"取的是**降服、收住**的意思，不是降级。整套内容反复在做一件事：**把手里的新技术压到工程可控的范围内**。

体现在三个具体动作上：

1. **锁版本，不追最新。** 生产基线钉在 **v1.1.2.2**，`v2.0.0-M1.1` 只作为观察线。理由在第 1 掌说得很直白：很多 `NoSuchMethodError` 不是 bug，是选型决策的迟到账单；把 pre-release 用在生产，等于把版本风险转嫁给业务方。
2. **先画边界，再比功能。** 把 Spring AI、Spring AI Alibaba Extensions、Agent Framework、Graph Runtime、Admin/Studio 五层摆正位置，先回答"我这个需求该落在哪一层"，再讨论用哪个模块。
3. **能不加就不加。** 第 1 掌专门留了一节讲"什么时候不加框架"：只需要文本补全，Spring AI 基础抽象就够；连多轮对话都不需要，普通 Java 服务加一次 HTTP 调用就是最优解。**框架的价值只在需求跨过阈值时兑现，跨不过去时它就是纯负担。**

## 四、这套系列怎么读：三条路线，别按顺序硬啃

18 掌是**一条依赖链**，不是 18 篇并列的文章。跳着读会踩两个坑：掌 N 用到的契约是掌 N−1 冻住的；掌 N 的"排查"章节复现的是掌 N−1 留下的故障。

### 路线 A｜正在选型、还没动手（架构师 / 技术负责人）

```
第1掌 识势选型 → 第9掌 ReactAgent → 第10掌 百阵流程 → 第13掌 跨域A2A → 第15掌 试炼评测
```

读这一条，你拿到的是**决策依据**：Agent 该不该上、上到什么程度、Flow Agent 写死编排和自主推理怎么取舍、MCP 与 A2A 的边界到底画在哪、评测体系怎么建。

### 路线 B｜手上已经在做 AI 应用（后端 / 全栈）

```
第1掌 → 第2掌 筑基环境 → 第3掌 数字人底座 → 第4掌 御模对话 → 第5掌 藏忆流式
→ 第6掌 御器工具 → 第7掌 通玄MCP → 第8掌 入藏RAG
```

读这一条，你拿到的是**可直接复用的底座契约**：以 `projectId` 为公共锚点、管理链路与实时链路分离、理解推理只长在一处。第 3 掌有一句值得抄在工位上的话：*底座做得越薄，后面加得越快。*

### 路线 C｜准备上线、要做交付（SRE / 平台 / 测试）

```
第14掌 溯源源码（行为对齐） → 第15掌 试炼评测 → 第16掌 立派服务
→ 第17掌 观星治理 → 第18掌 登云K8s
```

读这一条，你拿到的是**可交付的证据链**：从"这个行为到底由哪一行代码决定"，到"六类回归集怎么建"，到"一条失败请求怎么在一条 traceId 上定位到模型 / Tool / RAG / Graph 节点 / 远程 Agent"，最后到"发版不掉线、Pod 挂了能自愈、发错了能回滚"。

## 六、几处最值得单独拎出来的判断

如果时间只够看五段，看这五处。每一处都是"反直觉 + 有证据"的写法。

**1）第 1 掌｜功能列表越长，选型越难做对。**
功能是可以后加的，边界一旦画错，后面每加一个功能都在加固错误的结构。判断阈值只需问三个问题：需不需要状态、需不需要工具、需不需要多步可控。三个都是"不需要"，就别上 Agent 那几层。

**2）第 3 掌｜实时链路里，"少一跳"常常是负优化。**
把 LLM 放在实时进程里直连模型，看起来延迟更短、代码更少，但 Tool 注册、RAG 检索、Agent、Graph 全都长在 Spring Boot 侧。实时进程一旦自己直连模型，就会长出第二套上下文和第二套工具注册表——**后面每一掌都要改两遍。**

**3）第 6 掌｜模型从来不执行代码，它只写参数。**
所以**提示词不是安全边界**。在 System Prompt 里写"请不要随意修改数据"，只是一条概率约束：它降低出事的概率，但不改变出事的能力。能力面的收窄必须靠结构，不能靠语气。

**4）第 13 掌｜MCP 管能力，A2A 管主体。**
边界不是"新协议和老协议"，也不是"对内和对外"，而是**能力归属**：MCP 的被调用方是没有目标的工具；A2A 的被调用方是有自主性的主体，它可能自己再调工具、再拆任务、多轮追问，返回的是一个有生命周期的任务。

**5）第 15 掌｜测试的边界就是 mock 的边界。**
把 `ChatModel` 整个 mock 掉，等于在测试里写死一个假设："模型永远会返回我们期望的那段文本"。而在真实世界里，这个假设恰恰是最不成立的——**模型的输出本来就是要被验证的对象，不是背景条件。**

## 七、视频怎么看

18 集视频与 18 篇文章一一对应，**都在腾讯云开发者社区**，主题相同、侧重不同：

- **文章**：完整可复现——环境与版本、依赖与配置、排查过程、可验证的完成标准；
- **视频**：竖屏成片，单集 3～5 分钟，用"13 人圆桌"推演的方式把这一掌的**决策过程**讲一遍——为什么这么定、否掉了哪些方案、红线画在哪里。适合通勤时看，看完再回文章里抠细节。

建议的搭配节奏：**先看视频拿到这一掌的取舍，再读文章落代码**。反过来先读文章，容易在细节里迷路而错过决策本身。

视频与文章在社区里互为配套：打开任意一集视频，都能顺着同一掌的文章找到这一掌的完整工程细节；反过来从文章进来，也能直接跳到对应那一集视频。

## 八、适合谁读，不适合谁读

**适合你，如果：**

- 你在做 AI 应用或者 Agent 应用，技术栈是 Java / Spring Boot；
- 你已经在选型 Spring AI、Spring AI Alibaba、AgentScope、LangChain4j，需要一份带证据的对比口径；
- 你的项目已经"能跑"，但一加需求就要动结构，团队不敢往上叠；
- 你要交付、要上线、要被评测，而不仅仅是做个演示。

**不适合你，如果：**

- 你只想找一份"10 分钟写出第一个 ChatBot"的快速入门——官方文档和 examples 更快；
- 你用的是 Python 技术栈——这套内容里除了第 7、13 掌的协议部分，其余都是 Spring 侧的工程决策；
- 你在找一键可跑的完整仓库——这套内容给的是**契约与判断**，不是成品框架。
