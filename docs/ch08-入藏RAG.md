# 第 8 掌 · 震惊百里 · 入藏 RAG：隔离是数据建模，不是检索质量

> 对应文章：<https://cloud.tencent.com/developer/article/2752097>
> 分支：`chapter/08-rag` ｜ 标签：`ch08`

## 一、这一掌要解决的问题

第 3～7 掌的数字人已经会聊天、会记忆、会调工具，但它仍然只能「凭知识回答」——
客户问「你们开放时间几点」，它只能编一个像样的时间。

这一掌把项目知识接进来。而接知识最容易踩的坑不是「检索不准」，是**串库**：
把两个项目的文档一股脑灌进同一个向量库，用 A 项目的问题检索时，
很可能召回 B 项目的「客户专享折扣」，然后数字人用 A 项目的口吻讲给 A 项目的客户听。

文章里那句话值得原样记住：**隔离没做对时，最先炸的不是「答不出来」，而是「答得太流利」**。
拒答会有人来问，串库不会触发任何告警，只消耗信任。

## 二、四条可验证的完成标准（本掌逐条落）

| # | 标准 | 本掌怎么落 |
|---|------|-----------|
| 1 | 每条 chunk 都带 `projectId` / `docName` / `chunkIndex` | 切分后**重建**元数据（不假设 splitter 帮我带过去），写入后立刻回读校验 |
| 2 | 任意项目检索只返回本项目 chunk | `projectId` 是检索方法的**必填参数**，不提供无过滤重载；命中后再复核一次归属 |
| 3 | 回答带引用，且来源可映射到文档 | 上下文按 `[n] 来源=docName#chunkIndex` 渲染；接口另返回**系统渲染**的 `sources`，不依赖模型自觉 |
| 4 | 无相关内容时明确拒答 | 无命中（或全部低于相关度下限）→ **不调用模型**，直接返回 `refused=true` |

## 三、链路与边界

```text
[写入] Document(projectId+docName) → Splitter → 重建 chunk 元数据 → 契约校验
         → VectorStore.add → 回读校验(按 projectId 过滤查回来) → 写真源表 knowledge_document
[检索] projectId(必填) + question → topK=检索预算, threshold=0 → filterExpression(projectId == 'X')
         → 命中归属复核 → 相关度下限筛选 → 截断到展示条数
[回答] 无命中 → 拒答（不调模型）
         有命中 → [n] 来源=docName#chunkIndex 渲染上下文 → 模型 → 答案 + 系统渲染的 sources
```

三圈边界：

- **写入侧**：元数据契约在这里固化；缺字段直接拒绝入库，不静默通过；
- **检索侧**：`projectId` 是唯一且必填的过滤入口——**可以绕过的边界等于没有边界**，
  所以不提供无过滤重载（把运行时约束变成编译期约束）；
- **回答侧**：来源由系统渲染，模型可能漏标引用，接口调用方不能漏。

## 四、两个参数陷阱（文章里的真实坑）

1. **`topK` 不是结果数，是候选池大小**。先保证「正确 chunk 进得来」（预算 20、阈值 0），
   再由业务侧截断到展示条数（4）。把 topK 当结果数用，是「一加过滤就一条都查不到」的常见根因。
2. **阈值调高是「突然答不出来」的头号嫌疑**：中文短问句与长 chunk 的余弦相似度普遍不高，
   0.5 这种阈值会先把正确候选筛掉。所以向量库阈值设 0，另设一个**业务侧相关度下限**
   （`min-score=0.01`）专门用来判断「有没有依据」。

第二条里有个必须说清的区分：**相关度判据不是隔离手段**。
用「提高阈值」去解决串库，方向从一开始就错——它只会把所有项目的短答案一起误杀，
然后模型在空上下文里自由发挥，等于把一个明显的故障（串库）换成一个更隐蔽的故障（编造）。

## 五、向量库是投影，不是真源

本仓库用的是内存实现 `SimpleVectorStore`：重启即空、多实例各存一份。
文章的遗留问题清单里就有这一条，本掌的处置不是假装看不见：

```text
真源：knowledge_document（MySQL）—— 哪个项目有哪些文档，是业务事实
投影：VectorStore（内存）—— 可丢弃、可按真源重建（KnowledgeVectorReloader 启动时重建）
```

好处很实在：换 embedding 模型、换向量库、扩容重建索引，都不用动业务数据。
生产环境仍应换持久化向量库（PGVector / Redis / AnalyticDB），
并按文章要求**逐库核验过滤语义是否一致**。

## 六、向量化用的是「词法」实现（必须说清楚）

本环境没有可用的向量化服务：DeepSeek 只提供对话模型（实测 `/models` 只有两个 chat 模型），
DashScope 没有可用密钥。按第 1 掌立的规矩（**不留不可验证的通道**），
本掌没有引一条配了但没法验证的 embedding 通道，而是用本地确定性实现
`HashingEmbeddingModel`（中文字符二元组 + 英文词的哈希特征，词频加权 + L2 归一化）。

| | 说明 |
|---|---|
| 它是真的 | 链路（切分→向量化→存储→过滤检索→增强→引用）全部真实；隔离与溯源也真实 |
| 它是词法的 | 不理解同义与改写（「多少钱」与「价格」在它眼里无关），**召回率不代表生产水平** |
| 怎么换 | 换掉 `embeddingModel` 这一个 Bean（DashScope text-embedding-v3 / OpenAI / 本地 ONNX），调用方一行不改 |

最后一行不是空话：这正是 Spring AI 抽象买到的东西，也是本掌能验证的部分
（`RagConfig` 里换 Bean，`KnowledgeIngestService` / `ProjectKnowledgeRetriever` / `RagAnswerService` 都不动）。

## 七、与文章的差异（如实记录）

1. **文章的向量化用 DashScope**，本仓库用本地词法实现，原因见第六节；隔离与溯源这两条验收与文章一致。
2. **文章把「无命中拒答」体现在 Prompt 里**（让模型说「资料里没有」），本仓库把它做在**代码里**：
   没有依据连模型都不调。理由是拒答是产品行为，不该由模型的服从性决定；
   文章第 09 节其实也是这个方向（「来源归系统」「无据不轻信」）。
3. **文章的例子是 CRM FAQ 文档**，本仓库用「展厅参观手册 / 客户专享政策」两份真实文档，
   正好覆盖串库场景（A 项目不能答出 B 项目的折扣与热线）。
