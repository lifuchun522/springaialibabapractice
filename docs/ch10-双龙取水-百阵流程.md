# 第 10 掌 · 双龙取水 · 百阵流程：流程是确定的，就别再交给采样来决定

> 对应文章：<https://cloud.tencent.com/developer/article/2752095>
> 分支：`chapter/10-workflow-agents` ｜ 标签：`ch10`

## 一、这一掌要解决的问题

第 9 掌把主脑换成了 ReactAgent，演示很好看：一句话进来，它自己决定先检索还是先查业务系统。
试运行的第二天，产品同学提了三条要求——售前走咨询话术、售后走工单流程；知识库与业务系统**同时**查；
用户没说清是哪台设备时必须追问。

这三条该写进 System Prompt，还是写成 Java 代码？

第 9 掌的真实数据给了答案：**同一个问题问 20 次，工具调用路径是会变的**——检索走不走、走几次，
是模型每一轮采样出来的。第 8 掌已经演过一遍同类事故（阈值 0 让「无依据拒答」永不触发），
这一掌的事故形态是：**该查的没查、该问的没问，而你在日志里没有任何可观测点**。

因为失败点藏在自由文本的推理里：没有节点，就没有埋点，也就没有证据。

## 二、四条可验证的完成标准（本掌逐条落）

| # | 标准 | 本掌怎么落 | 证据 |
|---|------|-----------|------|
| 1 | 同一问题连续二十次，顺序模式节点序列完全一致 | `understand → retrieve → answer` 用 `SequentialAgent` 固定；「跳过检索」在结构上不存在 | 离线 20 次断言 + 真实 20 次调用 |
| 2 | 并行两条分支都有独立产出，且互不覆盖 | 分支各写自己的状态键（`knowledge_hits` / `biz_records`），归并是**显式节点** | 响应里 `outputs` 三个键都在 |
| 3 | 售前、售后各十组样本，路由命中正确 | `LlmRoutingAgent` 只做一次分类；口径里写死「只能返回一个分支」 | 20 组真实样本 + 原始 TSV |
| 4 | 每次响应都能打印经过的节点名与各自耗时 | 节点聚合视图（耗时/输出条数）+ 序列视图（顺序） | 每次响应都带 `nodes` 与 `sequence` |

## 三、链路与边界

```text
[入口] POST /api/projects/{id}/workflow/{ask|sequential|parallel|loop}
   → 账本落一笔 USER（第 5 掌的规矩，这里不重复）
   → 按**节点**裁剪工具集合（结构问题，不是提示词问题）
   → 走对应编排：
        ask        : LlmRoutingAgent(presale | aftersale | fallback)
        sequential : understand → retrieve → answer
        parallel   : (knowledge-query ∥ biz-query) → merge(代码) → answer
        loop       : LoopAgent( Sequential(check-completeness → ask-back) ) × 最多 2 轮
   → 按节点埋点（聚合视图 + 序列视图）
   → 账本落一笔 ASSISTANT → 返回 {reply, branch, nodes, sequence, outputs}
```

三圈边界：

- **控制流**：谁在什么条件下跑，写死在 Java 里。编排只回答「谁跑」，不回答「内容怎么生成」。
- **语义**：意图分类、答案组织、追问措辞仍然是 LLM。**唯一的例外是归并**——它只是把两份材料拼起来，
  属于控制流（见第四节第 1 条）。
- **能力**：每个节点拿到的工具是**按名字裁剪**的。检索节点只有检索工具、理解节点一个工具都没有，
  「这个节点不该干的事」在结构上做不到，而不是写在提示词里求模型配合。

## 四、四件事只有自己写一遍才知道

### 1. 分支写自己的 key，就看不上下游的 Agent 了

文章里说「两条分支写独立 key，再加一个汇总节点读取两者做合并」。第一版我照做：
两个分支各写 `knowledge_hits` / `biz_records`，再挂一个 `merge` 的 ReactAgent 节点。
真实跑出来的归并结果是：

```json
{"merged_material":"当前未收到上游两条分支的具体内容，因此无法判断…"}
```

**根因**：`outputKey` 把产出写到自定义状态键，**就不会再进 `messages`**；
而下游 Agent 节点的提示词是从 messages 拼的，于是它什么也看不到。
两条分支的结果都在状态里躺着，归并节点却在说「没收到」。

处置：**归并改成代码节点**——直接读两个键、按固定格式拼接、缺哪边写哪边缺失。
这不只是为了修 bug：归并本来就是「把材料放一起」，不需要语义判断，
**不是每个节点都必须由模型来跑**。归并出的材料再作为输入交给回答节点收口成一个字符串。

### 2. 框架的 `fallbackAgent` 不覆盖「分支名不存在」

文章说「边界之外必须留出口」。框架的 `LlmRoutingAgent` 有 `fallbackAgent(...)`，
我挂了它，然后让模型返回一个不存在的分支名——**框架直接抛异常**：

```console
Failed to get valid decision after 2 retries. Last invalid decision: [not_a_branch]
```

也就是说：模型答非所问时，请求会变成 500，而不是走兜底。
处置：出口由我们接住——路由整体失败时直接跑 `fallback` 节点。
离线用例 `routed_shouldFallBackWhenModelPicksAnUnknownBranch` 钉住这个行为。

### 3. `LoopAgent` 只收一个 sub-agent，而且连写两次会**互相覆盖**

第一版按文章写成 `.subAgent(check).subAgent(clarify)`，跑出来只有 `clarify` 在跑，
`check-completeness` 的产出整个不见了。框架的报错说得很直白：

```console
LoopAgent must have only one subAgent, please use subAgent() method.
```

处置：把「检查 → 追问」这一对先组合成 `SequentialAgent`，再把它交给循环。
顺带说明四类 Flow Agent 是**可以互相嵌套**的，不是四个互斥的模板。

### 4. 节点埋点必须按节点聚合，不能一条输出一行

框架用 `stream` 吐节点输出：一次简单调用会产生**上百条** `NodeOutput`，
并行分支还逐条交错，而且 `NodeOutput.node()` 是内部节点 id
（`_AGENT_MODEL_`、`_AGENT_HOOK_InstructionAgentHook.before`、`__START__`）。
真正对应「哪个节点在跑」的是 `NodeOutput.agent()`，形如 `subgraph_understand`。

处置：埋点按 **agent 名（去掉 `subgraph_` 前缀）聚合**，给出时间跨度与输出条数，
另存一份「序列视图」（连续同名只记一次）。两个视图各回答一个问题：
聚合视图回答「各花了多久」，序列视图回答「顺序是否可复现、循环跑了几轮」。
并行分支的时间跨度互相重叠——这恰好是「并行真的并行了」的证据。

## 五、关于路由命中率：口径含糊时，命中率是骗人的

第一版口径只写了「产品能力、价格、试用、选型、私有化部署」，20 组样本命中 **17/20**。
三条 MISS 是：

| 样本 | 我的标注 | 实际分支 |
|------|----------|----------|
| 你们展厅几点关门？ | aftersale | presale |
| 深圳展厅还有停车位吗？ | aftersale | presale |
| 展馆周一开门吗？ | aftersale | presale（澄清前是 fallback） |

看清楚了：这三条都是**参观咨询**（开放时间、停车、是否营业），
模型把它们判成售前是合理的——**是我的标注和口径对不上，不是模型答错**。
把口径写清（参观类信息显式归 presale）后重跑，同一批答案按修正后的标注读就是 **20/20**。

这件事的真实结论比「命中率 100%」更重要：

- 路由命中率的分母取决于**样本标注口径**；口径含糊时，这个数字既不能用来夸模型，也不能用来骂模型；
- 想把「改了编排之后到底变好还是变坏」说清楚，需要**评测集**——这是第 15 掌的事，
  本掌只把「可复现、可埋点」这两件事做实。

## 六、本掌的取舍（写清楚代价）

- **并行不总是更快**：两条分支同时跑，token 是叠加的。只有两条结果都要用，并行才划算；
  如果有一条注定被丢掉，那就是纯浪费（文章 9.4）。
- **循环在同步请求里转不出新信息**：没有「用户的下一次回答」，第二轮的重新检查只是自检。
  它的价值是**有界**这个结构保证，以及为第 11 掌的可中断状态打地基——不假装它已经能跨轮追问。
- **编排之外的开放问题只能兜底**：确定性流程最大的风险是把不属于任何分支的问题硬塞进某个分支，
  所以 `fallback` 必须有，而且它可以是（也应该是）一个能力更宽的节点。
- **每个请求重新构建 Agent**：与第 9 掌同因（身份要闭包、工具要按节点裁剪），代价也同因。
