# 第 4 掌 · 鸿渐于陆 · 御模对话：把「用哪个模型」挪进数据

> 对应文章：<https://cloud.tencent.com/developer/article/2752104>
> 分支：`chapter/04-chat-model` ｜ 标签：`ch04`

## 一、这一掌要解决的问题

客户 A 用一家模型没问题，客户 B 要求换一家。翻代码才发现：业务类里 import 了一行某家 SDK 的
`XxxChatOptions`——**就这一行，把「换模型」从一次配置变更，变成了代码变更**。

于是这一掌的验收标准写得很硬（照文章口径）：

1. 同一个对话接口，**只改数据里的 provider 与 model**，就能切换模型，不重新编译、不重启；
2. 业务包里**不出现任何 provider 专有类型的 import**；
3. 鉴权失败、超时、上游不可用三类错误都有确定的响应体，**不允许退化成默认 500 页面**；
4. 切换模型前后，运行页表现一致。

## 二、三圈边界

```text
[输入] POST /api/projects/{id}/chat {text}
    |
    v
[业务层] ChatController → DigitalHumanChatService
         只认 ChatClient / ChatOptions / String，不认任何一家 SDK
    |
    v
[适配层] ChatOptionsFactory  ← 整个工程里唯一出现 OpenAiChatOptions 的地方
         ChatClientConfig    ← 唯一装配 ChatClient 的地方
    |
    v
[配置层] agent_config(provider, model, system_prompt, temperature, max_tokens)
         digital-human.models  ← 模型目录（有哪些 provider、每个 provider 下有哪些模型）
```

两条反直觉判断，也是这一掌真正想讲的东西：

- **ChatClient 不是「某家模型的客户端」**。它内部没有 socket、没有鉴权，真正连出去的是 ChatModel；
  把它当成某家的客户端，方向从一开始就反了。
- **模型名不是路由键，provider 才是**。`deepseek-flash` 只是 deepseek 这个 provider 下面的一个普通字符串；
  请求打到哪个 endpoint、用哪套鉴权头，跟模型名没有任何关系。把模型名当路由键用，
  第 1 掌那套抽象就白做了。

## 三、模型目录与启动期校验

模型清单是配置，不是枚举常量：

```yaml
digital-human:
  models:
    - id: deepseek-flash
      provider: deepseek
      display-name: DeepSeek V4.1 Flash
    - id: deepseek-v4-pro
      provider: deepseek
      display-name: DeepSeek V4 Pro
```

两个校验点：

- **启动期**：目录为空、provider 缺失、条目重复 → 直接启动失败（`ModelCatalog` 的 `@PostConstruct`）。
- **改配置时**：`PUT /api/projects/{id}/agent` 会先查目录，模型不在目录里就返回 400 并列出可用项——
  而不是等运行页被点开才发现模型名写错（这正是文章第 06 节那条「200 但内容为空」排查链的根因处置方式）。

## 四、参数键要按 provider 核验，不能照抄

实测（2026-09-28，DeepSeek OpenAI 兼容接口）：

| 请求参数 | HTTP | 实际效果 |
|----------|------|----------|
| `max_completion_tokens: 16` | 200 | **被忽略**：`completion_tokens` 实际 94，回答完整 |
| `max_tokens: 16` | 200 | **生效**：`finish_reason=length`，`completion_tokens=16` |

所以 `ChatOptionsFactory` 里落到 `maxTokens`，并在单测里显式断言
`getMaxCompletionTokens()` 为空——把「我们发的是哪个键」钉成回归项。
换 provider 时这段结论必须重新核验，不能想当然。

## 五、错误分类：不谈「异常」，谈「确定的响应」

| 上游情况 | 我方 kind | HTTP | 响应体 |
|----------|-----------|------|--------|
| 密钥被拒（401 / InvalidApiKey） | `AUTH` | 502 | `{error, type: MODEL_AUTH, provider, model}` |
| 连接/读取超时 | `TIMEOUT` | 504 | `{error, type: MODEL_TIMEOUT, provider, model}` |
| 限流、上游 5xx | `UNAVAILABLE` | 503 | `{error, type: MODEL_UNAVAILABLE, provider, model}` |
| 其它上游错误 | `PROVIDER_ERROR` | 502 | `{error, type: MODEL_PROVIDER_ERROR, provider, model}` |
| **200 但内容为空** | `EMPTY_RESPONSE` | 502 | `{error, type: MODEL_EMPTY_RESPONSE, provider, model}` |

业务代码不 catch 任何一家 SDK 的异常体系（那等于把两家的报错都写死），
调用点统一收敛成 `ModelInvocationException`，由 `ApiExceptionHandler` 翻译成上表。

最后一类值得单独说：**「200 但内容是空字符串」是最容易伪装成成功的失败**。
它是真实存在的——第六节就是用 `maxTokens=16` 逼出来的。

## 六、与文章的差异（如实记录）

1. **文章用 DashScope + DeepSeek 两家做双 provider 演示**，本仓库当前只有 DeepSeek 一条通道，
   所以 `ChatOptionsFactory` 里只有 `deepseek` 一个分支。**但这不等于抽象白做**：
   多出来的东西是真实存在的——`provider` 字段、模型目录、按 provider 造 Options 的入口、
   业务包零 provider import，这四条都已经在测试里钉住；加第二家 provider 是加一个分支 + 一段配置，
   不需要动业务层与接口。
2. **文章的对话接口是 `POST /api/digital-humans/{id}/chat`**，本仓库沿用第 3 掌的资源命名
   `POST /api/projects/{id}/chat`，接口形状（`{text}` → `{reply}`）与文章一致。
3. **文章把 model 参数写在 `DigitalHuman` 这条记录上**，本仓库在第 3 掌已把它拆成一对一的
   `agent_config` 表，本掌在这张表上加了 `provider` 列（Flyway V2），没有改主键关系。
