## 四、DashScope 通道：本掌不提供（不可验证的通道不留）

系列基线是 DashScope，但当前环境没有可用的 DashScope 密钥。用现有密钥直连 DashScope 复核过：

```console
$ curl -X POST 'https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions' \
    -H 'Authorization: Bearer sk-***' -d @ds-probe.json
{"error":{"message":"Incorrect API key provided. ...","code":"invalid_api_key"},
 "request_id":"cb3c1b6f-2bc0-99f5-ac2c-9aea925d74ed"}
__HTTP__401
```

结论：网络链路正常（请求到达 DashScope 并被应答），问题在密钥归属——该密钥属于 DeepSeek，不是 DashScope。
按文章第 06 节第二条排查链的口径，这就是「401 现象的根因在密钥来源对齐」。

处理方式：本掌**只引入 DeepSeek 通道**，不引入「引了但不用、启动期还要密钥」的 DashScope starter；
等需要它的章节（第 3 掌语音、第 8 掌 Embedding）再按章引入。

## 五、核验中发现的与文章不一致之处

1. **BOM 不是一个，是两个。** 文章第 02 节写「依赖交 BOM 统一管理」，实测
   `spring-ai-alibaba-bom:1.1.2.2` 只管理 `agent-framework`、`graph-core`、`studio`、`sandbox`、
   `starter-a2a-nacos` 等；`spring-ai-alibaba-starter-dashscope` 由
   `spring-ai-alibaba-extensions-bom:1.1.2.2` 管理。只引入前者会在构建期报
   `'dependencies.dependency.version' ... is missing`。本仓库两个 BOM 都引入，作为后续章节的版本地基。
2. **模型 SDK 是启动期 fail-fast 的。** 密钥缺失不是「调用时才报错」，而是启动即失败
   （`OpenAI API key must be set`）。这符合文章「把校验前移到启动期」的主张，但也意味着
   无密钥环境下服务无法以「降级态」启动——这一点留给第 18 掌的生产化课题。
3. **版本基线可核验。** SAA 1.1.2.2 的 POM 显式声明 Spring AI 1.1.2 与 Spring Boot 3.5.10，
   本仓库按该组合对齐；`2.0.0-M1.1` 为 Pre-release，按文章口径不进生产。
4. **踩坑记录：陈旧的 `target/test-classes` 会伪造失败。** 删除 `src/test/resources/application.yml`
   后未 clean，Maven 仍加载旧副本，导致「两个 ChatModel bean」的假故障；`mvn clean test` 后消失。
   结论：改配置类资源文件后必须 clean，否则验证结论不可信。
