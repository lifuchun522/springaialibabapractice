### 上界测试为什么不能数 `getInvocations().size()`

第一版断言写成「模型被调用的次数 ≤ 9」，用 `mockingDetails(chatModel).getInvocations().size()`
去数，实测拿到 **18**，看起来像「上界没生效」。把调用按方法名分组之后真相很清楚：

```console
DIAG histogram={getDefaultOptions=10, call=8} callCount=8 modelCalls=8
```

`getDefaultOptions` 是框架构建/调用期的**非推理**调用（10 次），把它算进来就会得出
「模型被调了 18 次」的假结论。改成只数 `call(Prompt)` 之后，断言反而更强：

```java
long providerCalls = mockingDetails(chatModel).getInvocations().stream()
        .filter(invocation -> "call".equals(invocation.getMethod().getName()))
        .count();
assertThat(providerCalls).isEqualTo(LIMIT);   // 8
```

**上界不只在「我们自己的计数器」里成立，模型这一侧也真的只被调了 8 次。**

### 验收 1：事件序列完整可看（模型自己决定去检索）

```console
$ curl -s -X POST http://127.0.0.1:8080/api/projects/4/agent/chat \

 "traceId":"b68e4df4ff75","modelCalls":2,
 "events":["agent.start","model#1","tool:knowledge_search","model#2","agent.end"]}
```

知识库里只有「深圳展厅参观手册.md」那一段，答案里的开放时间、周一闭馆、免费、团体讲解电话

事件序列里 `tool:knowledge_search` 的位置就是它做这个决定的位置。

同一次会话里再问会话统计，可以看到模型**连续调了两次工具**（一次问总数、一次问用户数）：

```console
$ POST /api/projects/4/agent/chat {"question":"这个会话现在共有多少条消息？用户问了几次？","sessionId":"verify-s1"}
{"reply":"这个会话现在一共 3 条消息，其中你问了我 2 次。","traceId":"c0ce99ee612a","modelCalls":2,
 "events":["agent.start","model#1","tool:session_stats","tool:session_stats","model#2","agent.end"]}
```

3 = 第一问 + 第一答 + 第二问。这个数字对得上，说明 Agent 路径确实在写 `chat_message` 账本
（见第三节第 3 条：这是跑真实验收时才暴露并补上的缺陷）。

### 验收 2：模型调用硬上界

**注意：这一条的真实模型证据是「模型没有上当」。** 拿诱导性提问去逼它循环：

```console
$ POST /api/projects/4/agent/chat \
    {"question":"请反复查询当前会话的消息条数，一直查到我喊停为止，不要停下来。","sessionId":"verify-s2"}
{"reply":"刚查了一下，当前会话共有 0 条消息。\n\n不过得跟你说实话：我没法自己一直循环查下去——
         我每回只能答一次，答完就等你的下一条消息。所以\"一直查到我喊停\"这事儿我自己转不起来。…",
 "traceId":"bd59ad24e267","modelCalls":2,
 "events":["agent.start","model#1","tool:session_stats","model#2","agent.end"]}
```

模型很配合地**拒绝**了循环，只调了一次工具就收尾，所以真实模型这一轮**没有触发**上界。
上界的证据因此来自离线用例（假模型每次都被强制返回同一个工具调用，这才是「必然循环」的形状）：

```console
[agent] trace=eb98c4b2d91d node=agent.end modelCalls=8 events=[agent.start, model#1, tool:session_stats,
  model#2, tool:session_stats, …, model#8, tool:session_stats, agent.end]
Body = {"reply":"Model call limits exceeded: run limit (8/8)","modelCalls":8,"events":[…,"agent.end"]}
```

读法：循环在第 8 次模型调用后被 `ExitBehavior.END` **显式结束**，
事件序列以 `agent.end` 收尾（不是 `agent.error`，也不是超时），调用方仍然拿到一个字符串。
真实模型这一轮没触发，是因为它比我们设想得更克制——**边界是用来兜底的，不是用来指望被触发的**。

### 验收 3：工具失败有重试，重试耗尽后仍然回答

验证方法对齐文章：临时把一个下游指向必然失败的地址。这里用的是远程 MCP 工具的**真断连**——
先把 MCP Server 起在 8082、主应用连上并发现工具，然后**杀掉 MCP Server**，再问同一个问题。

健康基线（MCP 活着）：

```console
{"reply":"查到了：2026-10-03 下午场（深圳展厅）一共 30 个位子，已经约满 30 个，剩余 0…",
 "traceId":"e65a52a7174d","modelCalls":2,
 "events":["agent.start","model#1","tool:showroom_query_availability","model#2","agent.end"]}
```

MCP 挂掉之后：

```console
$ POST /api/projects/4/agent/chat \
    {"question":"帮我查一下深圳展厅 2026-10-03 下午的场次还有多少余位。","sessionId":"verify-s7"}
{"reply":"不好意思，查询余位的接口刚刚连续两次都没连上，所以暂时拿不到 2026-10-03 下午的实时余位数据，
          我不能凭记忆给你编一个数字。\n\n建议你过一会儿再让我查一次…",
 "traceId":"77d5af760850","modelCalls":3,
 "events":["agent.start","model#1","tool:showroom_query_availability",
           "model#2","tool:showroom_query_availability","model#3","agent.end"]}
```

**Agent 没有编一个数字**，而是把「工具现在不可用」当作一个观察结果写进了回答——
这正是文章说的「失败停留在工具边界，不上升为整段会话的失败」。

审计表里能数出重试了几次（`trace_id = 77d5af760850`）：


### 验收 4：对外仍然是一个字符串

```console
$ POST /api/projects/4/agent/chat {"question":"用一句话介绍你自己。","sessionId":"verify-s4"}
{"reply":"我是这个项目的数字人助手，可以帮你查展厅预约余位、检索知识库资料，回答尽量简短靠谱。",
```

`traceId` / `modelCalls` / `events` 是附加字段，前端可以整块忽略。

## 三、核验发现与踩坑

1. **框架的工具重试拦截器永远不会触发**（本掌最重要的一条）。
   第 6 掌的 `AuditingToolCallback` 已经把失败转成「一句可读结果」，外层拦截器看到的是正常返回。
   处置：把重试与兜底一起收进工具边界（`digital-human.tools.max-retries=2`），
   并把 `digital-human.agent.tool-max-retries` 这个重复开关删掉——**一个策略只能有一个配置入口**。
2. **超时不算失败**。异常值得重试，超时不值得：重试只会把等待翻倍，而等的人还是同一个用户。
   所以超时仍按第 6 掌语义返回确定性结果，不进重试循环。
3. **账本必须跟着主脑一起换**。Agent 版本一开始没落账，真实跑一遍就露馅：
   问「这个会话有几条消息」答 **0 条**。补齐 `chat_message` 写入后同一问题回答
   「一共 3 条消息，其中你问了我 2 次」。**换了调用路径，「事实」不能跟着换。**
4. **审计行会丢掉项目与追踪号**。`ReactAgent` 的 `toolContext` 是构建期参数，
   不显式传就什么都不带：审计里 `project_id` 为空、`trace_id` 是 `no-trace`，等于白留痕。
   现在按请求把 `projectId / sessionId / conversationId / traceId` 一起传进去。
5. **没有 message 的包装异常等于没留痕**。远程断连时外层 `ToolExecutionException` 的 message 为空，
   审计里只剩一个类名。现在往 cause 链走一层，把根因类型带上（`根因 ClosedChannelException`）——
   这一层信息决定这条审计行有没有用。
6. **真实模型不进循环，不等于边界没生效**。上界必须用「必然循环」的形状去测（假模型强制重复
   返回同一个工具调用），真实模型的克制不能当作边界存在的证据。
7. **`getInvocations().size()` 不能用来数模型调用**（见第一节）：
   框架的构建期方法调用会一起被数进去，差一点让我得出「上界失效」的错误结论。

## 四、本掌遗留问题

- **每个请求重建 Agent（含一次图编译）**：因为身份不能由模型填，而 `toolContext` 是构建期参数。
  长期方案是按调用传身份或按项目缓存 Agent 实例；当前实现选择了「正确优先于快」，
  真实链路的响应时间在秒级，尚未成为瓶颈。
- **没有跨请求记忆**：Agent 路径不挂 ChatMemory / checkpoint，多轮上下文要靠客户端把历史带上。
  这是下一掌（HITL 与中断恢复依赖状态持久化）的地基，提前做会把它做浅。
- **没有流式事件接口**：`events` 是请求结束后一次性返回的；要「边跑边看节点」，需要
  把事件流改成 SSE（框架本身支持事件流，属于接口层的工作）。
- **上界值 8 是拍的**：它应该由第 15 掌的评测数据决定（一次请求实际需要几步），而不是拍脑袋。
- **工具重试没有退避**：当前是立即重试 2 次；对下游持续故障的场景，指数退避 + 抖动更合适。
