## 二、真实环境验收

### 验收 1：顺序模式，同一问题 20 次节点序列完全一致

```console

节点序列：qa-sequential,understand,retrieve,answer,qa-sequential
```

20 行原始输出在 `evidence-ch10/runB-acc1-sequences.txt`（20 行完全相同）。

而现在顺序是结构给的——`retrieve` 想被跳过，在图上都没有那条边。

### 验收 2：并行两条分支各有独立产出

```console
branch=parallel
nodes=parallel-recall(18873ms) → knowledge-query(3423ms) → biz-query(18855ms)
      → merge(0ms) → answer-with-material(11942ms)
outputs 键：knowledge_hits, biz_records, merged_material
```

`knowledge_hits`（知识库原文 + 来源 `数字人产品手册.md#0`）与
`biz_records`（业务系统的结构化 JSON，含 `status=PENDING_PARAM`、`missing_param=fromDate`）
两份内容完全不同 → 没有被互相覆盖。

**修复前**（`evidence-ch10/runA-BEFORE-FIX-parallel-merge-empty.json`）：两个键都在，
但归并节点的产出是「当前未收到上游两条分支的具体内容…」——`outputKey` 把产出写到了自定义键，
就不再进 `messages`，下游 Agent 什么都看不到。改成代码归并后才拿到上面这份回答：

```console
reply=这周三还有没有位置，现在还查不了：业务系统缺 fromDate，没法确定「本周三」是哪一天，
      需要你给当前日期或明确目标日期；知识库里也没有具体余位、可约时段或名额。
      …知识库能确认的只有：深圳展厅可预约参观，工作日 9:00–18:00 开放，周一闭馆。
      [1] 知识库片段：数字人产品手册.md#0
      [2] 业务系统：showroom_availability
      [3] 业务系统：visit_reservation_policy
```

两条分支的材料都进了最终回答，并且各自标了来源。

### 验收 3：售前 / 售后各 10 组样本的路由命中

这一条跑了 **5 轮**，结论比「命中率多少」重要得多（原始 TSV 都在 `evidence-ch10/`）：

| 轮次 | 路由温度 | 应用日志 | 命中（按最初标注） | 与上一轮逐条比对 |
|------|----------|----------|--------------------|------------------|
| runC | 未固定（默认） | 澄清口径后 | 17 / 20 | — |
| runD | 未固定 | 修埋点采集时机后 | 16 / 20 | **1 条翻转** |
| runE | 未固定 | 同 runD | 16 / 20 | 与 runD 一致 |
| runF | **0** | 只固定路由温度 | 17 / 20 | — |
| runG | **0** | 同 runF | 17 / 20 | **20 条判定完全一致** |

两次改动的意义分别说：

**（1）口径含糊时，命中率是骗人的。** runC 的三条 MISS 是
「你们展厅几点关门」「深圳展厅还有停车位吗」「展馆周一开门吗」——
都是**参观类信息**（开放时间、停车、是否营业），而我的**标注**把它们放进了售后。
模型判成售前是符合口径的：**是标注错了，不是模型错了**。
把口径写清（参观类信息显式归售前）后，同一批答案按修正后的标注读就是 **20 / 20**。

**（2）分类真的有方差，所以要固定温度。** runD 与 runC 之间有一条样本（「展厅这周三下午还有空位吗」，
按口径明确属于售后的「预约余位」）在两次运行里翻了面。这条不是标注问题，是**采样方差**：
路由分类的输出会被代码当条件用，不能有采样自由度。
固定 `route-temperature: 0` 之后重跑两轮，20 条判定**完全一致**，翻转消失。

这里也顺手印证了文章那句「分类比规划稳得多」：**稳是相对的**——
比让它输出一串动作序列稳得多，但仍然是采样，仍然需要把温度压下去。

### 验收 4：每次响应都能拿到节点名与耗时

```console
# 顺序
nodes=qa-sequential(14438ms) → understand(4708ms) → retrieve(2308ms) → answer(7411ms)
# 并行（两条分支的时间跨度互相重叠 —— 这就是「并行真的并行了」的证据）
nodes=parallel-recall(18873ms) → knowledge-query(3423ms) → biz-query(18855ms) → merge(0ms) → answer-with-material(11942ms)
# 循环（同一节点跨轮，跨度覆盖两轮）
```

每个节点还带 `emissions`（输出条数）——流式下一个节点会吐几百条输出，

## 三、核验发现与踩坑

1. **`outputKey` 与 `messages` 是互斥的**：分支写了自己的键，就不会再进消息历史，
   下游 Agent 节点在提示词里看不到（表现为模型答「未收到上游内容」）。
   处置：归并改成**代码节点**——它本来就只是把材料放一起，不需要语义判断。
2. **框架的 `fallbackAgent` 不覆盖「分支名不存在」**：模型返回一个不在清单里的分支名时，
   框架抛 `Failed to get valid decision after 2 retries`，请求变成 500。
   处置：出口由我们接住，路由失败直接跑兜底节点。
3. **`LoopAgent` 只收一个 subAgent，且连续写两次会互相覆盖**：
   第一版 `.subAgent(check).subAgent(clarify)` 的结果是只剩 `clarify` 在跑，
   框架报错「LoopAgent must have only one subAgent」。处置：把「检查 → 追问」先组合成顺序体再交给循环
   —— 顺带说明四类 Flow Agent 可以互相嵌套。
4. **埋点要按节点聚合，不能一条输出一行**：一次调用会产生上百条 `NodeOutput`；
   而且 `NodeOutput.node()` 是内部 id（`_AGENT_MODEL_`、`_AGENT_HOOK_...`），
   真正有用的是 `NodeOutput.agent()`（形如 `subgraph_understand`）。
5. **埋点的采集时机写错，耗时全是 0**：先 `collectList().block()` 再遍历，等于流结束后才打时间戳，
   四个节点全是 `0ms`——看上去像「埋点没生效」，其实是采集时机错了。
   改成 `doOnNext` 里边到边记之后，就得到了上面那份真实耗时。
6. **分类需要固定温度**（见验收 3 第 2 条）：新增 `FixedOptionsChatModel`，
   只给路由这一次调用固定参数；生成类节点仍保留生成自由度。
7. **测试里模型桩要同时桩 `call` 与 `stream`**：编排节点走 `ChatModel.stream`，
   路由节点走 `ChatModel.call`；只桩一个会得到「模型返回 null」的假故障。
8. **验收 2 的桩必须每次返回不同文本**：所有节点返回同一句话时，
   「两条分支内容不同」这条断言永远是绿的——那是在骗自己。

## 四、本掌遗留问题

- **没有评测集**：路由命中率的分母取决于标注口径，本掌只能证明「结构可复现 + 温度固定后可稳定」，
  证明不了「改了编排到底变好还是变坏」——这是第 15 掌（试炼评测）的事。
- **循环在同步请求里转不出新信息**：没有跨轮用户输入，第二轮只是自检。
  真正的跨轮追问要等状态可持久化（第 11 掌的 checkpoint / 中断恢复）。
- **并行只做两条固定分支**：更一般的 fan-out（按 N 个数据源动态展开）需要图编排。
- **编排层仍是单进程单体**：跨服务拆解与分布式协同是第 13 掌的事。
- **每个请求重新构建 Agent**：身份要闭包、工具要按节点裁剪，代价与第 9 掌同因。
