## 4. 滚动可无损：真实终止时序

```text
== 终止期间的 SSE 长连接 ==
终止时机            : 流式请求发出后 6 秒（模型仍在生成）
docker stop 耗时    : 16.3s（等待在途请求收尾）
data 帧数量         : 416
是否出现 error 帧   : False
客户端是否拿到完整回答 : True

应用日志：
23:25:28.930 INFO o.s.b.w.e.t.GracefulShutdown - Commencing graceful shutdown. Waiting for active requests to complete
23:25:35.867 INFO o.s.b.w.e.t.GracefulShutdown - Graceful shutdown complete
23:25:35.897 INFO c.z.hikari.HikariDataSource - HikariPool-1 - Shutdown initiated...
23:25:35.911 INFO c.z.hikari.HikariDataSource - HikariPool-1 - Shutdown completed.
```

**这条是这一掌的门面**：SIGTERM（K8s 删除 Pod 时发的就是它）到达时正在生成的那条流，
**完整答完 416 个数据帧、零错误帧**，进程才退出。它同时验证了三件事：
`server.shutdown=graceful` 生效、`exec` 形式让 java 成为 PID 1（信号直达 JVM）、
连接池在请求收尾之后才关。

对照第 16 掌的 SSE 心跳：心跳解决「静默期被网关判死」，优雅退出解决「升级期被硬切断」，
两件事合起来才是「长连接服务能滚动发布」。

## 5. 状态可外置：记忆从 Pod 堆搬到账本

`chat_message` 账本本来就是真源（第 5 掌的边界），本掌把 Memory 的实现换成读它：

```java
// LedgerChatMemoryRepository
findByConversationId -> 读 chat_message（按 conversationId 三层键），只取 COMPLETED 的记录
saveAll              -> 有意为空（账本已经在每轮写入，再写一遍就是双份真源）
deleteByConversationId -> 删的是账本记录（不可逆，所以调用要谨慎）
```

实测（`LedgerChatMemoryRepositoryTest`）：

| 用例 | 断言 |
| --- | --- |
| 多副本不失忆 | 实例 B 只靠数据库就能读到实例 A 写入的两条历史 |
| 失败不进记忆 | `FAILED` / `CANCELLED` 的记录被跳过，只剩「问题一」「正常回答」 |
| 会话隔离 | 同一 sessionId、不同 userId 是两个会话，互不可见 |
| 写是有意空实现 | `saveAll` 之后账本记录数不变 |
| 空键安全 | `null` / 空白会话键返回空历史，不在请求路径上抛异常 |

为什么默认不是 `in-memory`：进程内记忆在单副本时看不出任何问题——
它恰好是最容易被默认值坑到的那类配置。测试与本地调试可以显式切回 `in-memory`。

## 6. 没验的部分（这一掌必须说清楚）

| 项 | 状态 |
| --- | --- |
| 真集群 `kubectl apply` / `rollout status` / `rollout undo` | **未验**（本环境无集群；`kubectl apply --dry-run=client` 也要连 API Server 做 discovery，实测报 `failed to download openapi`） |
| HPA 实际扩缩、PDB 在 `kubectl drain` 时的行为 | **未验** |
| Ingress 注解在真实网关上的效果 | **未验**（`proxy-buffering off` 等只做了结构校验） |
| 两个 Pod 之间的端到端会话连续性 | **未验**（只验到仓储层：两个实例共享记忆） |

替代手段是 `scripts/validate-k8s-manifests.py`：把这一掌的上线判据写成**可执行清单**
（liveness 路径、startup 探针存在、maxUnavailable=0、preStop、terminationGracePeriod≥60、
resources.requests、runAsNonRoot、只读根 + tmp/logs 挂载、记忆存储必须是 jdbc、
Ingress 关缓冲 + 长超时、HPA 缩容限速、PDB selector 命中 Pod 标签）。
它不需要集群就能跑，**结构对 ≠ 集群上跑通**，所以它放在遗留清单里而不是验收结论里。

## 7. 真实验收抓到的两个问题

### 7.1 `host.docker.internal` 在纯 Docker 下不解析（已定位）

第一次用 `--read-only` 起容器直接退出，日志第一段 Caused by 是：

```text
Caused by: java.net.UnknownHostException: host.docker.internal: Name does not resolve
```

与仓库既有结论一致（compose 注释里早写过「Linux 上 Docker 不会自动提供它」）。
修法是 `--add-host=host.docker.internal:host-gateway`；K8s 里直接用 Service 名，不会遇到这个问题。

**值得记一笔的原因**：容器内存不足、权限不对、网络不通在日志里都长成「启动失败」，
不看第一段 Caused by 就会往错方向修——我先怀疑了只读根文件系统，实际是 DNS。

### 7.2 只读根文件系统会连累日志目录（已修）

`readOnlyRootFilesystem: true` 之后，应用要写的目录必须显式挂出来（`/tmp` 与 `/app/logs`），
而且**镜像里也要先建好并 chown 给 10001**，否则在没有挂卷的场景（compose、本地 `docker run`）
启动就失败。镜像与 Deployment 两处现在都写了，注释里写明原因。

## 9. 遗留问题

1. 没有真集群验证：apply / rollout / undo / HPA / PDB / Ingress 都只做了结构校验。
2. 流水线有镜像构建与推送，**没有** `kubectl set image` 这一步（发布动作还没进 CI）。
3. HPA 按 CPU 扩缩：SSE 的并发由连接数决定，接了 Prometheus Adapter 后应按
   `genai_chat_seconds_count` 速率扩缩更准。
4. 多副本端到端会话连续性只验到仓储层，没验两个 Pod。
5. 「迁移写错且已应用」的恢复流程（Flyway repair + 回滚顺序）没有演练。
