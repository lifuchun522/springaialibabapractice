# 第 5 掌 · 潜龙勿用 · 藏忆流式：记忆是投影，历史是账本

> 对应文章：<https://cloud.tencent.com/developer/article/2752103>
> 分支：`chapter/05-memory-streaming` ｜ 标签：`ch05`

## 一、这一掌要解决的问题

前一掌的对话是**无状态**的：每次问「我叫什么名字」，模型都只能回答「不知道」。
而如果按最常见的方式补记忆——用一个全局 conversationId——两个浏览器会话立刻开始互相污染：
A 项目问「你好」，B 项目问「你好」，后端日志里 key 是同一个，两段对话被拼进同一次上下文。

所以这一掌同时处理三条线：**Prompt/Message 的组织、Memory 的隔离、响应式流到 Web 的桥接**。

可验证的完成标准（照文章口径，三条一起立）：

1. 同一会话有上下文，**两个浏览器会话不串线**；
2. Web 能以 `text/event-stream` 看到**增量**输出；
3. 产品历史**可独立查询**（按 projectId/sessionId 查回记录），并且取消要留痕。

## 二、一张图说清三个概念的分工

```text
[怎么做]   Prompt / System Message      ← 人设怎么说（第 3、4 掌的项目配置）
[看什么]   ChatMemory（窗口 20 条）      ← 模型短期能看到什么  ← 投影：可丢、可重建
[何时读写] MessageChatMemoryAdvisor     ← 织入 ChatClient 调用链
[怎么到 Web] Flux<String> → SSE          ← 增量下发
[记了什么] chat_message 账本             ← 产品事实：谁问过、答了什么、哪条没答完
```

**两条反直觉判断**（也解释了为什么两套东西必须都存在）：

- **ChatMemory 不是数据库**。它会被窗口裁剪、随重启消失、换实现就换语义。
  拿它当产品历史，等于把「账本」寄存在一个随时会变的缓存里。
- **模型名不是路由键，provider 才是**（第 4 掌）与**取消不是自动的业务语义**（本掌）是一类判断：
  客户端断开后，服务端最该做的是**留下状态**，而不是假装什么都没发生。

## 三、conversationId：一行规则，必须先定死

```text
conversationId = userId : projectId : sessionId
```

| 为什么 | 说明 |
|--------|------|
| 为什么三层 | 项目隔离 ≠ 会话隔离。同一项目下两个浏览器各有 sessionId，只按 projectId 做 key 必然串线 |
| 为什么缺失分量写成 `anon` / `0` / `default` | Advisor 一旦拿不到 conversationId，Memory 会全落到默认 key 上；显式占位能让它在日志里一眼可辨 |
| 为什么校验字符集 | sessionId 来自前端，限制为 `[A-Za-z0-9_-]{1,64}`，避免拼进 key 后无法排查 |

这条规则有独立单测（`ConversationIdTest`），因为它错了，后面所有体验、评测、历史都失去意义。

## 四、并发：同一会话串行，不排队、直接拒绝

同一个 conversationId 的 Memory 窗口是一份**有序状态**：两条请求并行进来，谁先写窗口是不确定的，
上下文顺序一乱，历史与回答就对不上。

做法刻意选得笨但确定：`ConversationGuard` 按 conversationId 做单飞（single-flight），
重复请求直接 **409 CONVERSATION_BUSY**。不排队的原因：排队会引入无上限等待与内存堆积，
而流式请求本来就有客户端这一层，重试比排队更容易解释。

## 五、取消、失败都要留痕

| 情况 | 账本里记什么 |
|------|--------------|
| 正常完成 | ASSISTANT + 完整内容 + `COMPLETED` |
| 客户端断开（`doOnCancel`） | ASSISTANT + **已收到的半截内容** + `CANCELLED` |
| 上游失败 | ASSISTANT + `[KIND] 错误摘要` + `FAILED` |
| 用户提问 | USER + 内容 + `COMPLETED`（请求一开始就落，保证「问过」这件事不丢） |

有了这三态，产品历史里就不会出现「一条永远没有回复的提问，而没人知道为什么」。

## 六、与文章的差异（如实记录）

1. **文章的 chat_message 表放在「优化」一节**，本仓库与 `chat_message` 一起做进本掌的 V1——
   因为三条验收线里「历史可独立查询」本来就是必选项，不做就没有验收依据。
2. **文章的并发处理是「按 conversationId 加锁或单消费者队列」**，本仓库选择**直接拒绝（409）**，
   理由见第四节；这是取舍，不是遗漏。
3. **落库是阻塞式 JPA，放在响应式回调里**（`doOnComplete` / `doOnCancel` / `doOnError`）。
   本掌先保证语义正确；生产化时应换成异步写入或 R2DBC，已写入遗留问题。
4. **文章用 `Flux<ServerSentEvent<String>>` 暴露 GET 接口**，本仓库沿用，并额外把流内错误映射成
   最后一帧 `event: error`：请求一旦开始，HTTP 状态码就固定了，此时抛 500 已经没有意义。
5. **前端用 fetch + ReadableStream 而不是 EventSource**：EventSource 在服务端关闭流后会自动重连，
   会把同一句问题重复问一遍。这个坑写在 `run.html` 的注释里。
