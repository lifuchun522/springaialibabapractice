# 第 16 掌 · 履霜冰至（立派服务）：把「跑得通」收成「能交付」

> 文章：[降SpringAI阿里第16掌-履霜冰至-立派服务](https://cloud.tencent.com/developer/article/2752087)
> 分支：`chapter/16-spring-service` ｜ 证据：`scripts/evidence-ch16/`
> 一句话：**跑得通的 Demo 不是服务，边界才是交付物。**

## 1. 这一掌做的不是加法，是收束

前十五掌一路在加能力：对话、记忆、工具、MCP、RAG、Agent、Graph、多 Agent、A2A、评测。
到这一掌，仓库里跑的已经是「一堆能演示的东西」，但还不是「一个别人敢部署的东西」。

四条判定线（文章 02 节的完成标准），本仓库逐条落地的位置：

| 完成标准 | 本仓库的落点 | 怎么验 |
| --- | --- | --- |
| 服务可独立启动 | `java -jar` 起得来；`DeploymentContractInitializer` 在启动前校验必需配置 | `scripts/evidence-ch16/01-startup-fail-fast.txt` |
| 能区分「进程活着」和「关键配置齐了」 | `/actuator/health/liveness`（只有 ping）与 `/actuator/health/readiness`（`configReadiness + db + diskSpace`） | `03-health-liveness.json`、`03-health-readiness.json` |
| 接口契约清晰 | 流式端点显式 `text/event-stream`、阻塞式显式 `application/json`、DTO 字段名被断言钉住 | `web/ApiContractTest` |
| 环境可切换、不改代码 | 全部配置走 `${ENV:default}`；`prod` profile 只改边界不改功能 | `application-prod.yml` + `web/ProdProfileBoundaryTest` |

## 2. 原理落成可执行的东西

这一掌的三条原理，如果只写进文档，下次「先让它跑起来」的临时改动就会把它们悄悄拆掉。
所以每一条都有一个可执行的化身：

| 原理 | 可执行的化身 | 违反时的表现 |
| --- | --- | --- |
| 分层的本质是**依赖方向**，不是目录结构 | `arch/LayeredArchitectureTest`（ArchUnit，6 条规则，进 CI 阻断） | 构建直接红，并指出哪一行代码反向依赖了 |
| 可交付的最小单位是「可独立启动 + 可自检」 | `config/DeploymentContract` + `ConfigReadinessHealthIndicator`（两者读同一份清单） | 缺配置时进程起不来，且错误信息点名环境变量 |
| 调试工具与用户前端不能混在一个产物里 | `/internal/llm/v1/**` 加 `@Profile("!prod")` | prod 下该路径 404，而不是「记得别开」 |

**为什么 ArchUnit 是这一掌最值钱的一行代码**：门禁第一次跑就抓到一处真实的反向依赖——
`web/ToolController` 直接注入 `ToolCallAuditRepository` 自己查库。它跑得通、也没人抱怨，
但它把「谁能读、读哪个项目的、怎么读」三件事混进了 HTTP 层，其它入口想复用只能再抄一遍。
修法是加一层 `service/ToolAuditService`（授权 + 查询是一个用例），依赖方向变成
`web → service → repository`。这类问题靠人眼 review 会漏，靠规则不会。

**分层不重命名包**：文章给出的七层叫法（api/application/agent/tool/rag/graph/infrastructure）
在本仓库的映射是 `web / service / agent+workflow+multiagent+graph / tools / rag+embedding / graph / config+repository`。
刻意不改包名——改包名是纯重命名，收益是「名字好看」，代价是前面十几掌的验收记录、
Wiki 与 tag 里的路径全部失联。**方向守住了，名字可以不同。**

## 3. 健康检查：探配置，不探依赖

`configReadiness` 只读环境里的配置项，**不做任何远程调用**。理由有两条，都是钱和噪声：

1. 被动探针会被按秒级频率打，每次都真调模型就是真花钱；
2. 模型侧抖动会把「我的服务没配好」和「对方今天不舒服」混成一个红点，运维照着排只会更慢。

两个健康分组的切法也有讲究，切错了比不切更坏：

- `liveness` **只含 ping**。一旦把配置或数据库放进来，配置一缺、库一抖，K8s 就会把还活着的进程
  反复杀掉重启，把「配置问题」放大成「服务雪崩」；
- `readiness` 含 `configReadiness + db + diskSpace`。缺任意一项都不该被挂进负载均衡。

`DeploymentContract` 是**唯一真源**：启动期校验与健康检查都读它。
两处各写一遍必然漂移，而「启动期认为必需、健康检查认为可选」这种不一致比不检查更坏——
它让你以为有人在把关。

## 4. SSE 契约化：心跳是契约，不是优化项

SSE 是长连接 + 小包。模型思考或工具执行期间可能几十秒没有下行数据，
任何一层网关的空闲超时都会把这种静默判成死连接——**直连正常、过网关就断**的「假流式」就是这么来的。

本仓库的落法是 `config/SseHeartbeat`：在真实数据流旁边挂一路周期性的**注释帧**
（`:heartbeat`）。用注释而不是数据帧，是因为注释按 SSE 规范会被客户端忽略——
它只负责让链路看到连接还活着，不参与内容。

这个类里有两个坑，都是踩了才知道的，也都是被测试抓住的：

1. **心跳必须跟着源流一起结束**。第一版写成 `Flux.merge(数据流, 心跳流)`，
   而 `Flux.interval` 永远不会自己结束——数据早答完了，合并后的流还开着，
   客户端表现为「内容完了但不关连接」，只能等超时。修法是用 `Sinks.empty()` 做
   「源已结束」的可重放信号，`takeUntilOther` 让心跳随之结束。
2. **源只能被订阅一次**。它背后是一次真实的模型调用，订阅两次就是花两次钱、生成两段答案；
   `Flux.defer` + 单次订阅是硬要求，不是风格问题。

## 5. 真实验收抓到的两个问题（本掌最有价值的部分）

### 5.1 空流被记成「正常答完」（已修）

压测长回答时撞上一次：服务端返回 200、连接正常关闭、**前端什么都没收到**，
而账本里这条助手消息被记成 `COMPLETED`（内容长度 0）。
同一次对话换成阻塞式接口，同样的问题会被明确判成 `EMPTY_RESPONSE` 失败。

同一个语义在两条契约上表现不同，就是交付契约没对齐；而对前端来说，
「没有回答」和「回答是空的」是完全不同的两件事：前者要重试提示，后者会静默地什么都不显示。
修法是流式路径补 `switchIfEmpty` 显式失败，账本记 `FAILED`，
证据与断言见 `service/EmptyStreamContractTest`。

### 5.2 默认异步执行器不适合生产负载（已修）

第一次带心跳跑真实流式请求时，日志里出现：

```text
Performing asynchronous handling through the default Spring MVC SimpleAsyncTaskExecutor.
This executor is not suitable for production use under load.
Please, configure an AsyncTaskExecutor through the WebMvc config.
```

它不会被任何功能测试挡住——功能全对，交付标准不过。这正是文章说的「Demo 能跑、交付不能」。
修法是 `config/WebAsyncConfig`：有界线程池（core 4 / max 32 / queue 200）、显式 5 分钟超时、
优雅停机（发版时不在半句话上掐断连接）。修复后同一条真实链路不再打印该警告
（修复前的警告原文见上，修复后的完整日志见 `scripts/evidence-ch16/02-app-run.log`）。

## 6. 与文章的差异（按本仓库基线核验后调整）

| 文章 | 本仓库 | 原因 |
| --- | --- | --- |
| 七层包名 `api/application/…` | 保留本仓库现有包名，只固定依赖方向并用 ArchUnit 守住 | 重命名会让历史验收记录、Wiki、tag 的路径全部失联 |
| `spring-ai-alibaba-studio` 的 profile 隔离 | 我们没有引入 Studio；对应风险面是 `/internal/llm/v1/**`（无鉴权、协议兼容、能驱动模型），同样用 `@Profile("!prod")` 挡住 | 判据相同：**访问它的人是不是开发者/内网组件** |
| `dashscope` 通道与 `${DASHSCOPE_API_KEY}` | 本仓库单通道 DeepSeek，必需项是 `${DEEPSEEK_API_KEY}` | 第 2 掌的取舍：只留一条可验证的通道 |
| LiveKit 实时语音与凭证签发 | **未实现**（第 3 掌起就记在遗留问题里）；本章只交付 REST + SSE 契约 | 本仓库的实时交互走 Bridge 契约端点 `/internal/llm/v1`，LiveKit 属于「没做的事」，不假装做了 |
| OpenAPI 描述生成（优化四） | 用**可执行的契约测试**替代：按 HandlerMapping 断言路径/方法/媒体类型，按 record 分量断言字段名 | 不引入生成器也能让契约「改名即红」；生成器路线列在遗留问题里 |
| K8s 探针清单 | 只做到 Compose 层（必需变量 `${VAR:?}` + 探针走 readiness）；K8s 清单留给第 18 掌 | 本章的判据是「部署清单里声明必需项」，不是「上 K8s」 |

## 7. 代价与适用边界

- **代价**：类的数量上升，「从 HTTP 请求到模型」的阅读路径从 1 跳变成 3~4 跳；
  部署清单、profile、契约测试都需要人维护。对单人 Demo 而言这是纯负担。
- **收益**：变更被隔离。改 Prompt 只动配置或 Agent；加接口只动 Controller + Service；
  换模型只动 `ai/ChatOptionsFactory`。运维靠 readiness 判断能否接流量，前端按契约联调。
- **适用条件**：当「使用这份代码的人」多于一个角色时，这笔开销才开始回本。只有一个角色时，你不需要它。

## 8. 遗留问题（诚实清单）

1. **LiveKit 实时语音未接**：凭证签发与会话生命周期都没做（承接第 3 掌的遗留）。
2. **契约描述没有生成器**：OpenAPI 文档需要引 `springdoc` 才能对外提供，本章只把契约做成了断言。
3. **K8s 探针与清单未落地**：留给第 18 掌；本章只到 Compose。
4. **健康检查不覆盖「模型是否真的可达」**：那是有成本的主动探测，不宜进被动探针；
   真要探，应做成独立的定时任务并把结果写进指标（第 17 掌的主题）。
5. **Tool / RAG / Graph 只是搬进了层里**：检索索引的加载时机与资源隔离仍未收口（第 8 掌遗留）。
