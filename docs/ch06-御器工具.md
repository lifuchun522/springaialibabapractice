# 第 6 掌 · 利涉大川 · 御器工具：模型只写参数，代码才动数据

> 对应文章：<https://cloud.tencent.com/developer/article/2752102>

## 一、这一掌要解决的问题

前五掌的数字人「说得挺好」，但它说的每一句都无法被验证：问它「这个会话有几条消息」，它只能编。
接上工具之后，「能调通」只是及格线——真正决定这套东西能不能对外开放的，是另外四件事：
参数校验、人类确认、审计、超时边界。

文章的六条完成标准，本掌逐条落：

| # | 标准 | 本掌怎么落 |
|---|------|-----------|
| 1 | 模型能选对工具并填对参数 | 真实模型端到端验证（见验收记录），工具描述写成可判断的契约 |
| 2 | 参数经 JSON Schema 校验后才进方法体 | 受限值域用 Java enum，Schema 里生成 `enum` 白名单；单测断言 Schema |
| 3 | 写工具在人类确认前不产生写库动作 | 只生成 `pending_title_change`，落库走人类确认这条确定性路径 |
| 4 | 每次调用都有审计（含追踪号） | `AuditingToolCallback` 装饰器统一包装，落 `tool_call_audit` |
| 5 | 同一确认令牌只能生效一次 | 令牌状态机 PENDING→CONFIRMED，重复确认 409 |
| 6 | 工具执行有超时边界 | 装饰器里 `Future.get(timeout)`，超时掐断并返回确定性结果 |

## 二、三条认知（比代码重要）

1. **模型从来不执行代码，它只写参数。** 模型输出的是一段 JSON，是我们的进程在跑函数。
   所以所有安全边界只能画在自己的代码里。
2. **提示词不是安全边界。** 在 System Prompt 里写「不要随意改数据」只是概率约束，
   它降低出事的概率，不改变出事的能力。能力面的收窄必须靠结构。
3. **身份永远不能由模型填。** 项目号、用户号走 `ToolContext` 旁路，不进 Schema；
   只要它出现在参数列表里，模型就有机会填成别人的。

本仓库额外加了一条自己的判断：**没有登录身份就不发写工具**。
第一版我用 `-1L` 给匿名请求占位，结果待确认记录挂在了假 owner 名下、人类确认时被判「不属于该账号」——
这是真实踩到的坑，修法是让「缺失就是缺失」，并在请求侧要求写能力必须带登录身份（401 而不是静默降级）。

## 三、两套工具、两种待遇

```text
只读工具（默认交给模型，模型想调几次调几次）
  getProjectInfo        项目标题/主题色/开场语/结束语
  querySessionStats     MESSAGE_COUNT / USER_MESSAGE_COUNT / LAST_MESSAGE_AT（enum 白名单）
                        returnDirect=true：结果直接作为最终回答，模型没有改写数字的机会

写工具（默认不交给模型，必须 allowWrite 显式请求，且带登录身份）
  proposeTitleChange    无令牌 → 只生成待确认记录；有令牌 → 校验并应用（单次有效）
```

## 四、审计与超时：一次装饰，全部生效

`ToolRegistry` 把每个 `ToolCallback` 包一层 `AuditingToolCallback`：

```text
模型写参数 → Schema 校验（框架） → 装饰器记开始时间
   → 线程池执行（超时上限内） → 记审计（工具名/参数/结果摘要/耗时/追踪号/身份）
   → 结果回灌模型 → 模型给最终回答
```

| 情况 | 给模型的结果 | 审计状态 |
|------|--------------|----------|
| 正常 | 工具返回值 | `OK` |
| 超过 `digital-human.tools.timeout-ms` | 「已被中止，请稍后重试」 | `TIMEOUT` |
| 工具抛异常 | 「工具执行失败：…」 | `ERROR` |
| 应用层拒绝（无身份/业务拒绝） | 明确拒因 | `ERROR` 或由工具自身返回 |

超时这条不是为了「性能」，是为了**一个卡住的下游不能把整条对话线程拖死**：
工具被掐断后对话还能继续，用户至少能得到一句「稍后重试」。

## 五、一个必须说清楚的测试边界

**工具执行循环不在 ChatClient 里，而在真实 ChatModel 实现内部。**
`OpenAiChatModel` 持有 ToolCallingManager：模型返回 `tool_calls` → 它执行工具 → 带上结果再问一次模型。

这意味着：用假的 ChatModel 根本测不出这个循环——写出来的只是自己编的循环。
所以本掌的测试分工是：

- **我们自己拥有的部分**用单测/集成测：Schema 生成、参数校验、工具执行、门禁、审计、超时、写工具状态机；
- **模型是否真的会选工具、填参数**交给真实模型端到端验证（`docs/ch06-验收记录.md` 有完整请求与响应）。

这个边界写在这里，是为了避免「测试全绿所以工具链一定对」这种结论。

## 六、与文章的差异（如实记录）

1. **文章的工具作用于外部业务系统（GetProjectInfo/QueryBusinessData/UpdateProjectTitle）**，
   本仓库用自己库里的真实数据实现同类工具（项目信息、会话统计、标题变更），
   好处是工具结果**可以被独立核实**（数据库里查得到）。
2. **文章的写工具在带令牌时由模型直接调用完成**，本仓库把落库收敛到人类确认接口
   （模型只能提议），理由见第二节第 3 条：模型对「讨论」与「指令」的区分是概率性的。
3. **文章提到的异步工具、returnDirect 细节**提示「以 v1.1.2.2 源码与官方文档为准」，
   本仓库实测确认 `returnDirect` 在 ChatClient 链路上生效（真实响应即工具返回值），
   并把这条写进测试与验收记录。
4. **文章把「按会话查消息」等能力放在例子工具里**，本仓库的统计工具默认统计**当前会话**
   （会话号来自 ToolContext），模型不填也能得到正确作用域。
