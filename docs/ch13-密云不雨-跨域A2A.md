# 第 13 掌 · 密云不雨 · 跨域 A2A

> 对应文章：<https://cloud.tencent.com/developer/article/2752092>

## 一、这一掌要解决的问题

前三掌把「一个进程内的编排」做扎实了（ReactAgent → Flow Agent → 状态图）。
但知识这件事本身有独立生命周期：它自己的数据、自己的发版节奏、自己的扩缩容需求。
继续放在主应用里，结果是**改知识库要重建数字人、知识域出事等于数字人整体不可用**。

这一掌把知识 Agent 拆出去，用协议协作，并且把三件事划清：

- **A2A 与 MCP 的边界不是「新协议 vs 老协议」，是能力归属**：MCP 的被调用方是能力提供者
  （工具、无状态、不自主）；A2A 的被调用方是**主体**（自己决定查什么、自己组织答案、有任务生命周期）。
  按这个口径，知识库检索适合 MCP，**知识 Agent** 适合 A2A。
- **A2A 的价值不是「把方法调用换成 HTTP」，是把远端的不确定性接进本地状态机**：
  任务什么时候算创建成功、谁有权取消、超时之后对方还在不在跑、重试是新建任务还是续跑——
  这些问题本地调用里不存在，跨服务里一个都不能回避。
- **注册中心是可选的中间层**：它只承载「谁能被找到」，不承载业务语义。

## 二、四条完成标准

| # | 标准 | 本掌怎么落 | 证据 |
|---|------|-----------|------|
| 1 | 两个独立进程，主服务不依赖知识 Agent 的任何类，只依赖协议 | 新增 `knowledge-agent` 模块（独立 jar、独立库 `knowledge_agent`）；主服务侧只有协议副本 + 客户端 | 两个 jar 各自启动，主服务类路径里没有对方的类 |
| 2 | 注册到发现中心后，多实例被分散调用且可观察 | `AgentRegistry` 接口两种实现（Nacos / 静态表），轮询选实例 | 连续 4 次调用：`8082 → 8083 → 8082 → 8083` |
| 3 | 一次协作有贯穿标识，超时/重试/熔断行为确定 | 请求头 `A2A-Trace-Id` 贯穿两端日志；只对「对方可能没收到」的失败重试（有界退避），**4xx 不重试** | `trace-correlation.txt`：同一条 traceId 在两份日志里对上 |
| 4 | 版本不兼容时失败显式、快速、可诊断 | 请求头 `A2A-Version` 与服务端不一致 → 409，消息里带两边版本 | 真实调用 `HTTP 409`；离线用例断言消息含两个版本号 |

## 三、架构与任务状态机

```text
[主服务 DH]  A2AController → A2AClient（发现 → 创建任务 → 流式消费）
                 ↓ 只依赖协议：AgentCard / Task / TaskEvent
[中间层]      AgentRegistry（Nacos 或静态表）—— 不承载业务语义
                 ↓ HTTP + A2A-Version + A2A-Trace-Id
[知识 Agent]  /.well-known/agent.json（能力声明）
              POST /a2a/tasks           → 202 + taskId（受理，不同步等）
              POST /a2a/tasks/{id}/events → SSE 流式（部分结果是合法中间状态）
              GET  /a2a/tasks/{id}      → 状态（卡在哪一步）
              POST /a2a/tasks/{id}/cancel → 取消（谁有权取消必须定义）
```

任务状态：`SUBMITTED → WORKING → COMPLETED / FAILED / CANCELED`。

## 四、核验发现与踩坑

### 1. 文章点名的三个 starter 在 1.1.2.2 里不存在

文章本身提示「坐标与 API 以官方文档核验」。实测（Maven Central）：

```console
spring-ai-alibaba-starter-a2a-server   → 不存在
spring-ai-alibaba-starter-a2a-client   → 不存在
spring-ai-alibaba-starter-nacos-discovery → 不存在
```

所以本掌**按协议语义自己实现了一层薄的 A2A**（能力声明 + 任务状态 + 流式 + 版本协商），
Nacos 只作为发现实现之一接 `nacos-client`。这不是绕路：
协议的三样东西（能力声明、任务、事件）本来就该由使用方定义清楚，而不是照抄一个坐标。

### 2. 「引入一个注册中心客户端」不是「加一个 jar」

`dependencyConvergence` **第四次**拦住东西：nacos-client → httpasyncclient → httpclient 4.5.13，
而 agent-framework 那边是 4.5.14。照旧统一到较高补丁版本——
门禁的价值就在这：这类分叉在单实例本地跑的时候完全看不出来。

### 3. 静态实例表用 YAML 列表绑不进 `@Value` 的 List（真实踩到）

第一次真实验收时「实例列表」只有一个元素，表现为**永远只打第一个实例**，
看起来像「轮询没生效」，实际是配置绑定问题：YAML 列表不会展开成多个元素。
处置：改成逗号分隔，并在注释里写明原因。

### 4. Spring 的 `${ENV:default}` 在环境变量为空时会给出空串

`enabled: ${A2A_NACOS_ENABLED:false}` 在环境变量存在但为空时，绑定到 boolean 直接报
`Invalid boolean value []`。处置：显式写 `false`，把开关方式写进注释——
**默认值要写在配置里，不要指望环境变量总是「要么有值、要么没有」**。

### 5. 已应用的 Flyway 迁移不能再改（这次是 CRLF 归一化）

第 11 掌已经踩过一次（改了 V6 内容）。这一掌又踩了一次，而且这次动的是 **V1**：
文件内容没改，但 Windows 上的换行归一化让 Flyway 算出的 checksum 与库里记录的不一致。
开发库的处置是 `flyway repair` 的等价做法（把历史记录 checksum 置空）；
工程上的结论只有一条：**迁移文件一旦被应用就当成只读**。

## 五、取舍与代价

- **一次本地调用变成三段开销**：序列化 + 网络往返 + 发现解析。本掌实测单次协作
  **0.9–9.4 秒**（首字延迟受对端 LLM 影响），而本地知识检索是毫秒级。
- **故障面从「一个断点」变成「跨两个服务的日志」**：所以贯穿 traceId 不是可选项。
- **任务有生命周期就有了「谁清理悬挂任务」**：本掌的任务表在内存里，重启即空（遗留问题）。
- **适用条件**：只有被拆出去的部分具备**独立生命周期、独立团队、独立扩缩容**需求时才划算。
  只是想让目录更整洁，把一个纯函数检索拆成服务，等于把复杂度换了个地方放。
- **本环境没有起 Nacos**：多实例分散调用是用静态表验证的，两条路径走同一个 `AgentRegistry`
  接口；Nacos 分支的代码与配置开关都在，但没有真实注册/订阅的落地证据（如实记录，不假装跑过）。
