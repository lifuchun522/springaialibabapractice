## 5. 真实验收抓到的四个问题（本掌最有价值的部分）

### 5.1 两套 traceId 抢同一个 MDC 键（已修）

**现象**：同一请求的响应头是 `a6d63cf3…`，日志里的 `traceId` 却是 `6d5f033b…`。

**根因**：Micrometer Tracing 的 correlation 装饰器**也往 MDC 写 `traceId`**（框架 span 的号），
而我的过滤器自己生成一个号也写同一个键——谁后写谁赢。

**修法**：过滤器**优先取框架当前 span 的 traceId**（与文章 V1 的写法一致），
没有 span 时才退回请求头/自生成。修后四者一致（第 4 节）。

**副产物**：`DiagnosticsControllerTest` 里原先断言「继承调用方 `X-Trace-Id`」的用例随之失效——
真实链路走的是 W3C `traceparent`（第 4 节已验证）。用例改成断言**应用内部一致**
（响应头 == 调用树 == 诊断接口），并在注释里写明为什么不在 MockMvc 里断言跨进程续链：
那是测试脚手架与真实容器过滤器顺序的差异，不是产品行为。

### 5.2 工具审计用的是另一套号，两张表 join 不上（已修）

**现象**：一次请求响应头 `9a3abf6d…`，而同一请求写进 `tool_call_audit` 的 trace_id 是 `c7c2b3418b6c`
（12 位，与 32 位的响应头号毫无关系）。

**根因**：`ConversationRequest` 无脑生成 12 位随机号，HTTP 侧却用 32 位号——
**两套身份系统并存**。工具审计是「模型到底调了什么」的唯一真相，join 不上等于链路断在最值钱的一段。

**修法**：`ConversationRequest` 先继承请求上下文里的 traceId，没有上下文（定时任务/内部调用）
才自生成；断言见 `service/ConversationRequestTraceTest`。修后 `08-tool-audit-trace.txt` 与响应头同号。

### 5.3 早失败得到一棵空树（已修，且连着两层坑）

项目不存在（404）、入参非法（400）这类错误在业务埋点之前就抛了，诊断面上什么都没有——
而空树恰恰出现在最需要答案的时候。**第一层修法**：在过滤器里给整个请求加一段 http 层调用。

加完之后发现它的 `failureType` 仍然是空的：**`@ExceptionHandler` 在 DispatcherServlet 内部就把异常
转成了响应，过滤器看不到任何异常**。**第二层修法**：http 层按响应状态码分类
（`FailureClassifier.classifyHttpStatus`，5xx 一律 UNKNOWN，不在这里猜层）。

### 5.4 失败分类的指标被静默丢弃（已修）

**现象**：日志里一行 WARN，业务一切正常，但 Prometheus 里查不到任何失败分类：

```text
WARN i.m.p.PrometheusMeterRegistry - The meter (MeterId{name='http.request', tags=[...,tag(failure.type=INPUT_INVALID),...]})
     registration has failed: Prometheus requires that all meters with the same name have ...
```

**根因**：Prometheus 要求同名指标的所有 meter 拥有**一致的标签键集合**；我原来只在失败时补
`failure.type`，于是带这个标签的那批 meter 被整批丢弃——**要聚合的东西被悄悄扔了**，
而且没有任何异常，只有一行 WARN。

**修法**：创建指标时就把 `failure.type=none` 写上，失败时改值不改键。修后实测：

```text
http_request_seconds_count{...,failure_type="INPUT_INVALID",layer="http",method="POST",path="/api/projects/999999/chat"} 1
http_request_seconds_count{...,failure_type="none",layer="http",method="GET",path="/api/chat"} 1
```

## 6. 与文章的差异

见设计文档第 5 节，摘要：**Admin 未接入**（用本地调用树 + Prometheus + 诊断接口替代，是遗留不是等价）；
OTLP 依赖与配置齐备但**本环境没有 collector**（日志里可见 `Failed to export spans`，端到端未验证）；
A2A 与 Graph 节点未做 span（沿用既有事件记录）；采样率默认 1.0 并注明演示规模。

## 7. 遗留问题

1. Admin（`spring-ai-alibaba-admin`）未接入：可视化、评测、MCP 管理都没落地。
2. OTLP 没有 collector：span 上报失败可见，链路端到端未验证。
3. A2A 远程调用与 Graph 节点未统一进调用树。
4. 诊断缓冲只在内存（默认最近 500 个 traceId），重启即空。
5. 没有按环境分层的采样策略。
