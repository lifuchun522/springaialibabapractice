## 一、这一掌要回答的问题

模型能调通不等于系统能上线。旧方案的典型形态是「HTTP 客户端直连模型 SDK + ConcurrentHashMap 存会话 + if-else 做工具路由」，
在单轮问答下是正确的，一旦需求变成**有状态、多步骤、可中断、可观测**，它就开始持续还债：

| 层 | 旧方案的表现 |
|----|--------------|
| 业务影响 | 改 System Prompt / 模型要重启发版；多 Agent 路由写在代码里，运营不可见 |
| 技术表现 | 会话与业务数据混存；工具无统一契约；流式与阻塞两套路径；换供应商要改调用层 |
| 可观测 | 只看到最终文本，看不到用了哪个工具、检索到什么、走了哪个分支 |

## 二、五层架构（本系列后续十七掌都落在这张图上）

```text
[输入] 运行页用户消息 / 后台配置
    |
    v
[模块] ChatClient 与 Model 适配  或  Agent Framework 编排
    |
    v
[数据/状态] 会话记忆 检索结果 图状态 检查点
    |
    v
[处理] 工具调用 MCP 检索 条件分支 中断恢复
    |
    v
[输出] 流式文本 运行追踪 评测样本
```

| 层 | 解决什么 | 输入 → 输出 |
|----|----------|-------------|
| Spring AI（基础抽象） | 怎么和模型说话、怎么把工具暴露给模型 | Prompt/Message → ChatResponse |
| Spring AI Alibaba Extensions | 厂商与生态适配：DashScope、MCP Registry/Nacos、Memory、RAG、Observation | 统一抽象 ↔ 阿里云生态 |
| Agent Framework | 把「一次模型调用」升级为「带钩子、可人工介入的执行单元」：ReactAgent、Hooks、HITL、Context Engineering、Skills | 目标 → 执行轨迹 |
| Graph Runtime | 长运行、有状态 Agent 的运行时：State/Node/Edge、条件与并行、Checkpoint、Interrupt、Streaming | 图定义 → 可恢复执行 |
| Admin / Studio | 可视化开发、追踪与评测 | 运行数据 → 可视与评测 |

两条反直觉判断：

1. **SAA 不是「更全的 SDK」，而是把 Agent 装配线分了层**。分层带来的不是功能，而是成本：只需要单轮问答时，分层是纯粹开销；只有当需求跨过单轮问答这条线，它才开始回本。
2. **Graph 不是拖拉拽画图工具，而是有状态执行的 Runtime**。要定时任务编排，用普通工作流引擎更省事；只有流程依赖 Agent 中间结果、需要挂起恢复，Graph 的存在才有意义。

## 三、选型判据（三个问题）

```text
需不需要状态？ 需不需要工具？ 需不需要多步可控？
三个都是「不需要」 → 停在 Spring AI 基础抽象，甚至普通 Java 服务 + 一次 HTTP 调用
跨过阈值          → 选 Spring AI Alibaba
已在 LangChain4j / AgentScope 有沉淀 → 不要为了换壳而迁移
```

## 四、版本基线（会变的事实，落地前按官方 Releases 核验）

| 项 | 取值 | 依据 |
|----|------|------|
| JDK | 21 LTS | Spring Boot 3.x 对 21 支持完善 |
| Spring Boot | 3.5.10 | `spring-ai-alibaba-starter-dashscope:1.1.2.2` 依赖 `spring-boot-starter:3.5.10` |
| Spring AI | 1.1.2 | SAA 1.1.2.2 的 autoconfigure 依赖 `org.springframework.ai:*:1.1.2` |
| Spring AI Alibaba | 1.1.2.2 | 系列指定的生产基线（官方 Latest 线） |
| 观察线 | 2.0.0-M1.1 | Pre-release，只观察，不进生产 |

> 核验方式：`spring-ai-alibaba-bom:1.1.2.2` 与 `spring-ai-alibaba-autoconfigure-dashscope:1.1.2.2`
> 的 POM 中显式声明了 Spring AI 1.1.2 与 Spring Boot 3.5.10，因此本仓库按该组合对齐，
> 不用「差不多最新」的版本组合。

## 五、本掌交付的工程结构

```text
spring-ai-alibaba-practice/          父 POM：只做版本管理，BOM 统一 Spring AI / SAA
└── digital-human/                   数字人最小骨架（后续十七掌在这上面长）
    └── src/main/java/com/example/digitalhuman
        ├── DigitalHumanApplication   启动入口
        ├── config/ChatClientConfig   模型调用唯一出口装配点
        ├── config/DigitalHumanChatProperties  System Prompt 外置为配置
        └── web/ChatController        只做参数校验与委派
```

三件收敛（对应文章第 07 节的 V2）：

1. **统一版本来源**：框架版本一律进 `dependencyManagement`，子模块不写框架版本号。
2. **配置外置**：System Prompt 与模型名是配置项，不是代码。
3. **出口唯一化**：控制器只依赖 `ChatClient`，禁止直接注入底层模型对象。
