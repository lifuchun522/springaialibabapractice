# 第 17 掌 · 羝羊触藩（观星治理）：一条失败请求到底死在哪一层

> 文章：[降SpringAI阿里第17掌-羝羊触藩-观星治理](https://cloud.tencent.com/developer/article/2752086)
> 分支：`chapter/17-observability-admin` ｜ 证据：`scripts/evidence-ch17/`
> 一句话：**日志是有的，但它在异步和跨进程面前失去了「归属」。**

## 1. 这一掌修的是「归属」，不是「数量」

可观测性不是「日志更多」，而是**在不理解内部实现的前提下，仅凭外部输出就能推断内部状态**。
文章那个反直觉判断值得抄下来：一百条没有共同 traceId 的日志是一百个孤立事实；
一百条共享同一 traceId 的日志才是**一条证据链**。前者让你更吵，后者让你更准。

四条完成标准，本仓库逐条落地：

| 完成标准 | 本仓库的落点 | 怎么验 |
| --- | --- | --- |
| 给定 traceId 能还原从入口到最内层的调用树 | `observability/SpanRecorder` + `web/DiagnosticsController` | `05-call-trees.md` |
| 树上每层都有开始/结束/结果 | `ObservedOperation` 在 http / model / tool / rag 四层埋点 | 同上（带 durationMs） |
| 失败能被归入明确分类，而不是统一的 Exception | `FailureType` + `FailureClassifier`（含按 HTTP 状态码分类） | `06-prometheus.txt`、`09-metric-failure-tag.txt` |
| 失败能定位到五层中的某一层并给出该层证据 | 诊断接口返回 layer + failureType + 耗时；审计表给工具层原始证据 | `05-call-trees.md`、`08-tool-audit-trace.txt` |

## 2. 身份四元组：四个号各回答一个问题

| 号 | 回答的问题 | 本仓库来源 |
| --- | --- | --- |
| `traceId` | **这一次**请求 | 框架当前 span 的 traceId（Micrometer/OTel），无 span 时退回 `X-Trace-Id` 头或自生成 |
| `projectId` | 哪个数字人 | `X-Project-Id` 头或查询参数 |
| `sessionId` | 用户视角的这一次对话 | `X-Session-Id` 头或查询参数 |
| `threadId` | Memory / 图检查点用的会话键 | `projectId:sessionId`（与第 5、11 掌的键保持一致） |

绑定方式刻意做成 **ThreadLocal + MDC 双写**：ThreadLocal 给代码读（诊断、审计），
MDC 给日志框架读（那一行身份）。日志格式因此在 `application.yml` 里定死：

```text
%X{traceId:--},%X{projectId:--},%X{sessionId:--},%X{threadId:--}
```

## 3. 真实验收抓到的四个问题（本掌最有价值的部分）

### 3.1 两套 traceId 抢同一个 MDC 键（已修）

第一版让过滤器自己生成 UUID。结果同一个请求出现两个号：**响应头与调用树**是 32 位
`a6d63cf3…`，而**日志里的 `traceId`** 是另一个 32 位 `6d5f033b…`。

根因：Micrometer Tracing 的 correlation 装饰器**也往 MDC 里写 `traceId`**，
写的是框架自己那条 span 的 traceId。同一个 key 被两套系统抢着写，日志和响应头就永远对不上。

修法就是文章 V1 里的写法：**优先用框架当前 span 的 traceId**，让身份只有一个来源。
修后四者一致（真实数据）：

```text
响应头 X-Trace-Id : 5acf194a627db0141eaf4e3c341cfa91
日志（入口线程）   : [5acf194a627db0141eaf4e3c341cfa91,1,ch17-align,1:ch17-align] GET /api/chat -> 200
日志（工具池线程） : [5acf194a627db0141eaf4e3c341cfa91,1,ch17-align,1:ch17-align] [tool] getProjectInfo 执行完成
审计表 trace_id   : 5acf194a627db0141eaf4e3c341cfa91
```

### 3.2 工具审计用的是另一套号，两张表永远 join 不上（已修）

`ConversationRequest` 原来无脑生成一个 12 位随机号作为 traceId，而 HTTP 侧用的是 32 位号。
实测：一次请求响应头是 `9a3abf6d…`，同一请求写进 `tool_call_audit` 的却是 `c7c2b3418b6c`。
**工具审计是「模型到底调了什么」的唯一真相**，它和日志 join 不上，等于链路断在最有价值的一段。

修法：`ConversationRequest` 先继承请求上下文里的 traceId，上下文没有（定时任务、内部调用）
才自生成。断言见 `service/ConversationRequestTraceTest`。

### 3.3 早失败会得到一棵空树（已修）

项目不存在（404）、入参非法（400）这类错误**在业务埋点之前就抛了**，于是诊断面上什么都没有——
空树恰恰出现在最需要答案的时候。修法是在过滤器里给整个请求加一段 http 层调用。

连环的第二个坑：加完 http 段之后，它的 `failureType` 仍然是空的。
因为 `@ExceptionHandler` 在 DispatcherServlet 内部就把异常转成了响应，**过滤器看不到任何异常**。
所以 http 层改成按**响应状态码**分类（`FailureClassifier.classifyHttpStatus`）：
HTTP 层的事实本来就是状态码。

### 3.4 失败分类的指标被静默丢弃（已修）

Prometheus 要求**同名指标的所有 meter 拥有一致的标签键集合**。我原来只在失败时补
`failure.type` 标签，于是「带这个标签的那批」被整批丢弃，日志里只有一行 WARN：

```text
WARN i.m.p.PrometheusMeterRegistry - The meter (MeterId{name='http.request', tags=[...,tag(failure.type=INPUT_INVALID),...]})
     registration has failed: Prometheus requires that all meters with the same name have ...
```

业务一切正常，指标里却查不到任何失败分类——**要聚合的东西被悄悄扔了**。
修法是在创建指标时就把 `failure.type=none` 写上，失败时改值不改键。修后实测：

```text
http_request_seconds_count{...,failure_type="INPUT_INVALID",layer="http",method="POST",path="/api/projects/999999/chat"} 1
http_request_seconds_count{...,failure_type="none",layer="http",method="GET",path="/api/chat"} 1
```

## 4. 埋点站在「必经之路」上

| 层 | 埋点位置 | 为什么是这里 |
| --- | --- | --- |
| http | `TraceContextFilter` | 唯一对所有请求（含早失败）都成立的位置 |
| model | `DigitalHumanChatService` 的 `answer` / `stream` | 两条契约都要覆盖——第一版只埋了阻塞式，结果运行页（流式）在诊断面上是空的 |
| tool | `AuditingToolCallback` | 工具调用的唯一入口；它同时是审计表的写入点，一份埋点喂两个下游 |
| rag | `RagAnswerService` | 无依据拒答在这里是**正常业务行为**，分类成 RAG_EMPTY 而不是故障 |

父子关系靠 `SpanScope`（线程上的「当前片段」）串起来，并且**和身份一起跨线程池传播**
（`ContextAwareTaskDecorator` / `ContextAwareExecutorService`）。
只传身份不传片段，工具片段会变成树上的第二个根——「都跑过，但看不出谁在谁里面」。

## 5. 与文章的差异

| 文章 | 本仓库 | 原因 |
| --- | --- | --- |
| Admin（`spring-ai-alibaba-admin`）承载可视化与 tracing | **未接入**；用「本地调用树 + Prometheus 指标 + 诊断接口」替代 | Admin 需要配套存储与服务组件，本环境没有；这是**遗留项不是等价替代** |
| OTLP 上报到采集后端 | 依赖与配置齐备（`micrometer-tracing-bridge-otel` + `opentelemetry-exporter-otlp`），但**本环境没有 collector**，日志里能看到 `Failed to export spans` | 不假装链路通了：真正的 span 后端验证要等有 collector 的环境 |
| Agent Hooks（ReactAgent 的 Model/Tool 回调） | 沿用第 9 掌已有的拦截器，第 17 掌补的是身份与分类；`AgentTrace` 仍是 Agent 路径的节点记录 | 不重复造一层 |
| Graph event / stream 取节点耗时 | 未做节点级 span（图路径仍是 `AgentTrace` 事件） | 记为遗留 |
| 采样率 | 配置为 `${TRACING_SAMPLING_PROBABILITY:1.0}` 并写明「演示规模全采，真实环境按流量调」 | 别把 1.0 当默认值抄走 |

## 6. 代价与适用边界

- **代价**：额外依赖与部署成本（OTLP 后端、指标存储）；采样成本；Hook 层的侵入仍需测试覆盖。
- **收益**：一次失败请求的定位时间从「小时」压到「分钟」；同类失败可聚合；上线前评估有数据可依。
- **适用条件**：一次请求跨越两个以上组件，或者跨越进程边界。只有一个模型调用、一条线程的
  Agent，`log.info` 确实够用，不必上这套。

## 7. 遗留问题（诚实清单）

1. **Admin 未接入**：可视化、评测、MCP 管理都没落地。
2. **OTLP 没有 collector**：span 上报失败在日志里可见，端到端链路未验证。
3. **A2A 与 Graph 节点未做 span**：远程 Agent 与图节点目前只有既有事件记录，没有统一进调用树。
4. **诊断缓冲只在内存**：默认保留最近 500 个 traceId，重启即空；长期留存要靠 OTLP 后端。
5. **采样与成本**：没有按环境分层的采样策略。
