## 二、真实环境验收

### 验收 1：图可视化

```console
$ GET /api/projects/{id}/after-sale/graph
{mermaid: "---\ntitle: after-sale\n---\nflowchart TD\n\t__START__ --> intent\n\tintent --> knowledge\n\t...
          risk -->|?| humanReview\n\trisk -->|?| reply\n\thumanReview --> reply\n\treply --> __END__\n..."}
```

结构由框架从真实的节点与边算出来——**改了边，图就跟着变**，不存在「图和代码漂移」。

### 验收 2 + 3 + 4：中断 → 重启进程 → 恢复

这是本掌最硬的一条证据，因为它跨了**进程边界**。完整步骤与观察点在
`scripts/evidence-ch11/RESTART-TEST.md`，这里只摘结论：

```console
# 第一次进入（高风险退款）：立即返回，没有阻塞等人工
$ POST /after-sale/run {"question":"我的订单 A20240617 想退款，已经签收了"}
status=INTERRUPTED threadId=3376ddbbcb014952
executedNodes=intent → biz → risk
riskLevel=HIGH  reply=（空，还没产生答复）

# 「这条工单卡在哪一步」——直接读检查点
检查点 4 条：
  __START__ → intent → __PARALLEL__(intent) → risk → next=humanReview      ← 卡在这里

# 杀掉应用进程（模拟发版），确认 8080 端口已空，检查点仍在 MySQL：
seq  node_id              next_node_id
1    __START__            intent
2    intent               __PARALLEL__(intent)
3    __PARALLEL__(intent) risk
4    risk                 humanReview

# 重新启动应用（新进程，内存 saver 是空的），拿同一个 threadId 恢复：
$ POST /after-sale/3376ddbbcb014952/resume {"decision":"APPROVE"}
status=DONE
executedNodes=humanReview → reply          ← 前面的节点**一个都没重跑**
reply=亲，你的订单 A20240617 退款申请，人工已经审核通过了，可以退。
      因为订单已签收，且已拆封商品按政策需要人工审核，这边已确认通过。…[0]

# 复查检查点：多了两条，next 走到 __END__
5    humanReview          reply
6    reply                __END__
```

三件事各有各的证据：

| 验收 | 证据 |
|------|------|
| 可中断 | `status=INTERRUPTED` 且**调用立即返回**；`executedNodes` 到 `risk` 为止，`reply` 没有跑 |
| 可恢复 | 恢复调用的 `executedNodes` **只有 `humanReview → reply`**——`intent`/`knowledge`/`biz`/`risk` 没重跑 |
| 状态可持久化 | 恢复发生在**杀进程之后新起的进程**里（`05-db-checkpoints-before-restart.txt` / `06-...-after-restart.txt` 两次数据库导出为对照）。内存 saver 这时是空的，能恢复只可能是因为状态从 MySQL 读回来了 |

时间线也对得上：中断发生在 `08:58:14`，人工决定落在 `08:59:41`——中间那次重启是真的。

## 三、核验发现与踩坑

1. **归约策略配错不报错，只丢数据**。这一条做成了可运行的反例（`StateReductionTest`）：
   同一张图、同样两个并行节点，只把 key 的策略从 `APPEND` 换成 `REPLACE`，
   产出就从 2 条变成 1 条，**没有异常、没有日志**。所以本仓库的规矩是
   「用到的每个 key 都显式声明策略，一个都不留给默认行为」。
2. **`threadId` 不一致＝恢复必重跑**。检查点按 `RunnableConfig.threadId` 索引，
   把它当业务字段持久化再读回来，表现就是「参数明明对，恢复就是从第一个检查点重跑」。
   本掌的规则：threadId 只在入口生成一次，业务层不持久化。
3. **「恢复」不是再调一次**：只传 threadId 会从头重跑；加了 `resume()` + `checkPointId` 之后
   变成原地再停一次（因为 `interruptBefore` 是编译进图里的规则）。
   最终形态是 `resume()` + `checkPointId(最后一个检查点)` + `withNodeResumed(断点节点)`。
4. **检查点不能按时间戳排序**。同一毫秒内会写好几条（`intent`、并行汇合、`risk` 挤在一起），
   按 `saved_at` 排序等于随机排序，恢复时就会挑错检查点。
   V6 建表时用自增 `seq` 记录写入顺序——这是被真实恢复失败逼出来的设计。
5. **判断「是否中断」不能只看 `next` 非空**：正常跑完时 `next` 是 `__END__`，
   第一版因此把每次正常结束都报成了 `INTERRUPTED`。
6. **读状态要用不带 checkPointId 的 config**。恢复用的 config 上带着旧的 checkPointId，
   拿它去 `getState` 只会看到旧快照，于是明明跑完了状态还报中断。
7. **并行分支里的普通节点不会单独产生 `NodeOutput`**：它和 Agent 节点在同一个 super-step，
   事件流里只看得见 Agent 那一格。于是「该查的没查」这种问题恰恰在事件流里看不出来
   （而这正是本掌要解决的事）。处置：节点把「我跑过了」写进状态里的 `nodeLog`——
   它跟着检查点落盘，**重启之后仍然知道之前跑过哪些节点**。
8. **返回空 Map 的节点同样不产生 `NodeOutput`**：知识库 0 命中时节点等于「隐身」了。
   处置：查不到也要显式写一条「已查询，0 条命中」——**「查了没有」和「没查」是两件事**。
9. **Agent 节点写自定义 key 时落进状态的是包装对象**，直接 `String.valueOf` 得到的是
   `com.alibaba.cloud.ai.graph.GraphResponse@121087b1` 这种对象地址，下游拿到等于什么都没拿到。
   处置：业务节点改走框架默认路径（写 `messages`），并**显式定义节点间输出契约**：
   业务记录 = 状态里最后一段可读的助手文本。读不出来时明确写「没有取到」，
   而不是把对象地址交给模型。

## 四、本掌遗留问题

- **节点间输出契约还没有完全解决**：Agent 节点留在状态里的结构（`GraphResponse` / `NodeOutput` /
  `Message` 的嵌套）目前只是「尽量读」，读不到就写「没取到」。真实运行里出现过读不到的情况，
  模型的反应是诚实地说「这次没取到业务记录」——不编造，但这仍是个缺口，
  应该由节点显式声明输出类型（下一掌接评测时一并定义）。
- **图结构没有版本化**：上线后改了图，历史检查点可能无法在新图上恢复。
- **检查点只增不删**：`graph_checkpoint` 会随运行时长增长，需要归档策略（未做）。
- **恢复只支持「人工批准/拒绝」这一种中断**：多类中断（补信息、二次确认）需要各自的恢复语义。
- **每个请求重建图**：与前两掌同因（工具要闭包项目身份），代价也同因。
