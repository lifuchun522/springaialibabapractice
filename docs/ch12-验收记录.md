## 二、真实环境验收（一轮跑完，原始产物在 `evidence-ch12/`）

```console
# 1) 知识类问题：路由直接命中知识角色
route=knowledge  hops=knowledge  memory={reception:0, knowledge:2, business:0}
reply=资料里查到的展厅开放信息如下 [1]：开放时间 工作日 9:00–18:00；周一闭馆；参观免费；团体讲解需提前三天预约…

# 2) 业务类问题（同一会话）：走业务角色，并诚实说明缺参数
route=business   hops=business   memory={reception:0, knowledge:2, business:2}
reply=我没法确定当前日期，所以「这周三」具体是哪天需要你确认一下。请告诉我具体日期（yyyy-MM-dd）…

# 3) 记忆边界：同一会话再问一句知识问题，接待与知识的记忆条数各自独立
route=business   hops=business   memory={reception:0, knowledge:2, business:4}

# 4) 寒暄类问题：走接待角色
route=reception  hops=reception  memory={reception:2, knowledge:0, business:0}
reply=你好！我是数字人「小盟」，这个项目的接待助手…

# 5) 同一会话内流转：寒暄之后换成知识问题 → 换角色，但接待记忆保持 2 条不被污染
route=knowledge  hops=knowledge  memory={reception:2, knowledge:2, business:0}
reply=不开门。资料里写的是「深圳展厅工作日九点到十八点开放，周一闭馆」[1]…
```

三条验收的对应关系：

| 验收 | 真实证据 |
|------|----------|
| #1 三角色协作、会话内流转 | 第 4、5 条：同一 `sessionId` 下 `reception → knowledge` 的角色切换；`hops` 字段就是轨迹 |
| #2 提示词 / 工具 / 记忆各自封闭 | `memorySizes` 每次都在响应里：接待轮只有 reception 增长，知识轮只有 knowledge 增长；`roleTools` 给出每个角色的工具清单 |
| #3 说清为什么必须多 Agent | 见 `docs/ch12-时乘六龙-分身多Agent.md` 第四节（上下文预算判据） |

## 三、核验发现与踩坑

1. **Router 误判是真实存在的代价，但边界能兜住**。第 3 条把「团体讲解提前几天预约」判给了业务角色
   （应该给知识角色）。这是文章点明的代价（「Router 的误判会让整条链路从一开始就跑偏」）。
   值得注意的是结果**没有变成事故**：业务角色只挂了会话统计与展厅预约两个工具，
   它明确回答「我这边没有这个口径或数据，不能凭猜测回答」，还顺手给了可做的下一步。
   **窄上下文 + 窄工具集让误判的后果被限制在「答不出来」，而不是「答错」。**
2. **工具不共享是硬约束，必须可断言**。`MultiAgentService.toolsAreDisjoint()` 把这条写成了可测的代码：
   共用工具意味着候选空间没有变窄，拆多 Agent 的第一收益就没了，只剩多次调用的成本。
3. **记忆命名空间不能用同一个 key**。三个角色共用 `sessionId` 做 key，就会退化成一份历史
   （第 5 掌的 `conversationId` 教训在这里换了个形态）。本掌用 `role:sessionId`。
4. **上界必须由代码握着**。角色是可以自主交接的，但只要有一个角色不停往外交接，
   没有 `max-hops` 就会一直跳下去；本掌还额外拒绝「跳回已经跳过的角色」。
5. **已应用的 Flyway 迁移不能再改**。本章真实验收第一次启动就撞上了：
   第 11 掌定稿前我在开发库里应用过 V6，之后又改了 V6 的内容，Flyway 校验直接失败
   （`Migrations have failed validation`）。这不是仓库缺陷（合并进 main 的 V6 是最终版，
   新库直接应用即可），而是**开发库的修复**：把该版本的历史记录 checksum 置空（等价于 `flyway repair`）。
   教训写在这里：**迁移一旦被应用就当成只读，要改就加新版本号。**

## 四、本掌遗留问题

- **角色记忆是进程内的**：`MessageWindowChatMemory` 重启即空，跨重启要接第 11 掌的持久化思路；
- **Router 是单点**：误判会跑偏整条链路，需要评测集来量化准确率（第 15 掌）；
- **角色之间没有共享的工作台**：当前靠 `handoff` 传一句提示，交接时该带哪些状态还没定义（输出契约，第 11 掌已埋下同类问题）；
- **建议路由的低置信度兜底未做**：分类结果落不进白名单时收敛到接待，但没有让用户感知到「可能判错了」。
