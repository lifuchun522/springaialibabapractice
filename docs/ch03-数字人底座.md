# 第 3 掌 · 见龙在田 · 数字人底座：把契约与表结构一次冻住

> 对应文章：<https://cloud.tencent.com/developer/article/2752105>
> 分支：`chapter/03-digital-human-demo`

## 一、这一掌要解决的问题

文章开头的两份代码都很典型：一份是单例 Demo，页面直接拿密钥调模型，配置全写死在 HTML 里；
另一份是本地 Python 语音脚本，答得挺流畅，但它不知道自己属于哪个项目。

两者的共同病根是**没有稳定的项目主键**。后面十七掌要做的记忆隔离、知识库隔离、Agent 隔离、会话隔离，
全都得挂在一个锚点上；锚点现在不定，第 5 掌加记忆要改表、第 8 掌加 RAG 要改共享方式、第 12 掌多 Agent 只能靠命名约定。

所以这一掌的动作很小、也很硬：**业务范围砍到最小，但链路边界与表结构一次画对**。

## 二、两条链路必须分开

```text
管理链路：Web 页面 → Spring Boot → MySQL
         只做 CRUD 与鉴权，不出网、不调模型、不碰音频

实时链路：Web ⇄ LiveKit ⇄ Realtime Bridge ⇄ Spring Boot / SAA
         LiveKit 只做 WebRTC 与音频/数据通道
         Bridge 只做音频编排与协议转换
         理解、推理、Tool、RAG、Agent 全部压在 Spring 侧
```

第二层的取舍是本掌最重要的结构决策：**把理解推理收回 Spring Boot，Bridge 只做音频与协议适配**。
代价是多了一跳内网 HTTP，收益是后面的 Tool / RAG / Agent 只在一个地方生长——
如果 Bridge 自己直连模型，就会长出第二套上下文与第二套工具注册表，后面每一掌都要改两遍。

## 三、冻结三张最小表

| 表 | 作用 | 关键约束 |
|----|------|----------|
| `users` | 账号 | `username` 唯一；只存 BCrypt 哈希，不存明文 |
| `digital_human_project` | 数字人项目：标题、主题色、背景图、开场白、结束语 | `owner_id` 索引；所有按 id 的操作都要带 ownerId |
| `agent_config` | 项目的一对一 Agent 配置 | `project_id` 唯一；本掌只用 `system_prompt` |

三张表由 Flyway 脚本 `V1__init_digital_human.sql` 建立，Hibernate 只做 `validate`——
**谁能改表结构必须唯一**，否则「实体随手一改、库结构跟着飘」是迟早的事。

为什么先冻表再冻接口：接口可以重命名、可以加字段，但表结构一旦被后续章节依赖，改动成本指数上升。

## 四、本掌交付与明确不交付

交付：

- 注册 / 登录 / 登出（BCrypt + 令牌，令牌通过 `X-Token` 头传递）
- 数字人项目 CRUD，带所有权隔离（别人的项目一律 404，不做「存在但无权」的区分，避免越权探测）
- `GET /api/projects/{id}/runtime`：运行页要的完整配置（项目 + Agent 配置）
- `GET /run/{projectId}`：运行页，配置由页面再拉接口获得，**改开场白不用发版**
- `GET /api/chat?q=&projectId=`：对话走项目自己的 System Prompt
- `POST /internal/llm/v1/chat/completions`：给实时语音 Bridge 用的 OpenAI 兼容端点（协议契约先立住）

不交付（明确记账，不装作已完成）：

- **LiveKit 实时语音**：需要 LiveKit Server + Python Bridge 两个额外进程，
  本掌只把 Spring 侧的契约（运行配置 + OpenAI 兼容端点）立好；语音链路的接入单独成章/单独 PR。
- **令牌持久化**：令牌存在进程内存里，重启即失效。这是文章定的 Demo 方案，
  代码注释与验收记录都写明「生产必须换成正式认证方案」，不假装它已经能上生产。
- **模型参数生效**：`agent_config` 里的 `model` / `temperature` / `maxTokens` 已随表冻结，
  但本掌只让 `system_prompt` 真正进链路；参数下发是第 4 掌（御模对话）的事。

## 五、测试策略：运行期 MySQL，测试期内存库

| 环境 | 数据源 | 表结构来源 |
|------|--------|------------|
| 运行 | MySQL 8（`DIGITAL_HUMAN_DB_*` 注入） | Flyway 迁移 + Hibernate `validate` |
| 测试 | H2（MySQL 兼容模式） | Hibernate `create-drop`，Flyway 关闭 |

理由：单测要能**离线、确定性**跑通，不该要求每个开发者先起一个 MySQL；而运行期必须是真库，
否则「改了实体没改迁移脚本」这类问题会被 H2 掩盖。两者的差异点写在这里，不藏在配置里。

```bash
# 运行期起一个本地 MySQL
docker run -d --name dh-mysql -e MYSQL_ROOT_PASSWORD=root -e MYSQL_DATABASE=digital_human \
  -p 3306:3306 mysql:8

# 测试期不需要数据库
./mvnw -B -ntp clean test
```

## 六、门禁第一次真的拦住了东西

引入 JPA 后，`dependencyConvergence` 直接让构建失败：

```text
Dependency convergence error for org.antlr:antlr4-runtime:jar:4.13.0 paths to dependency are:
+- spring-boot-starter-data-jpa → hibernate-core 6.6.41 → antlr4-runtime 4.13.0
+- spring-boot-starter-data-jpa → spring-data-jpa 3.5.8 → antlr4-runtime 4.13.0
+- spring-ai-starter-model-openai → spring-ai-model 1.1.2 → spring-ai-template-st 1.1.2 → antlr4-runtime 4.13.1
```

处置方式是**统一到较高的补丁版本（4.13.1）**，而不是关掉门禁或 exclude 掉其中一条路径——
这正是第 2 掌那把门禁存在的意义：它拦住的不是「错误」，而是「将来会以 NoSuchMethodError 形式出现的问题」。

## 七、与文章的差异（如实记录）

1. **文章用 `LiveKitTokenController` + Python Bridge 完成语音闭环**，本掌只落 Spring 侧契约（见第四节）。
2. **文章把令牌放在 `AuthController` 内部的 ConcurrentHashMap**，本仓库把它抽到 `AuthService`：
   控制器只做参数绑定与委派，令牌语义与密码策略集中在服务层，这样它才能被单测覆盖。
3. **文章的运行页是「一份可读配置 + 一个 LiveKit token」**，本掌的运行页先做文本问答闭环
   （开场白 / 结束语 / 主题色 / 背景图 + 对话），语音接入后同一页面再加音轨。
4. **文章示例里 `AgentConfig` 默认 System Prompt 是硬编码字符串**，本仓库改成从 `application.yml`
   注入默认值（`digital-human.chat.default-system`），延续第 1 掌「配置属于数据、不属于代码」的口径。
