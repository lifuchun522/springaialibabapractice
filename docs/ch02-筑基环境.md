# 第 2 掌 · 飞龙在天 · 筑基环境：把基线钉进仓库

> 对应文章：<https://cloud.tencent.com/developer/article/2752106>
> 分支：`chapter/02-baseline-env`

## 一、这一掌要解决的问题

文章开头的现场很典型：有人 JDK 8、有人 17、有人 21；有人手动加依赖，Spring AI 与 Extensions 版本对不上，
启动就报 `NoSuchMethodError`。这类问题的共同点是——**它们不是代码问题，却要花掉写代码的时间，而且每个人都要再花一次**。

第 1 掌已经给出了框架版本基线（BOM 统一管理），但「基线写在文档里」和「基线挡在构建门口」是两件事。
这一掌把基线从文档搬进门禁：**过不了门禁，代码就进不了仓库。**

## 二、三件事：锁 Maven、锁 JDK、锁依赖版本

| 要锁的东西 | 手段 | 失败时的现象（就是我们要提前拦住的） |
|------------|------|--------------------------------------|
| Maven 版本 | Maven Wrapper（`mvnw` / `mvnw.cmd`） | 各人机器上的 Maven 版本不同，构建行为不一致 |
| JDK 版本 | `requireJavaVersion [21,22)` | `UnsupportedClassVersionError: class file version 65.0` |
| 依赖版本 | BOM + `dependencyConvergence` | `NoSuchMethodError` / `NoClassDefFoundError`、自动配置失效 |

三件事都做成**可自动判定**的：前两件由 enforcer 在 `validate` 阶段检查，第三件由 `dependencyConvergence` 检查。

## 三、实测到的基线（可核验，不是抄文档）

```text
JDK          21.0.8 LTS
Maven        3.9.11（由 ./mvnw 提供，不用机器上的 mvn）
Spring Boot  3.5.10
Spring AI    1.1.2
SAA          1.1.2.2（BOM 版本基线；本掌未引入其 starter）
模型通道     DeepSeek（deepseek-flash）
```

版本关系不是猜的：`spring-ai-alibaba-starter-dashscope:1.1.2.2` 的 POM 里显式写着
`spring-boot-starter:3.5.10` 与 `org.springframework.ai:*:1.1.2`，本仓库按这对关系对齐。

## 四、为什么用 Wrapper 而不是「装一个 Maven」

`mvn` 依赖每个人机器上的安装；`./mvnw` 依赖仓库里的 `.mvn/wrapper/maven-wrapper.properties`。
前者的版本是「本机事实」，后者是「仓库事实」——只有后者能在新机器上复现。

本仓库用的是 `distributionType=only-script`（不往仓库里塞 wrapper jar），
首次执行时按需下载 Maven 3.9.11 到 `~/.m2/wrapper/dists/`：

```console
$ ./mvnw -v
Apache Maven 3.9.11
Maven home: C:\Users\<user>\.m2\wrapper\dists\apache-maven-3.9.11\d6d3cbd4012d4c1d840e93277aca316c
Java version: 21.0.8
```

另外补了 `.gitattributes`：`mvnw` 强制 LF。否则在 Windows 上提交、在 Linux/macOS 上克隆，
`./mvnw` 会直接报 `bad interpreter: No such file or directory`——这正是文章说的「环境差异导致的构建问题」。

## 五、新机器复现步骤

```bash
git clone <repo> && cd springaialibabapractice
export DEEPSEEK_API_KEY=sk-xxxx          # Windows: set DEEPSEEK_API_KEY=sk-xxxx
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\env-check.ps1   # Windows 自检
./mvnw -B -ntp clean test                # 模块级测试
./mvnw -pl digital-human spring-boot:run # 起服务
curl "http://localhost:8080/api/chat?q=用一句话介绍你自己"
```

`scripts/env-check.ps1` 会把「工具链 → 模型通道 → 构建测试」逐项过一遍，
任何一项不过就直接退出非 0：**先修环境，再谈代码**。它只打印密钥长度，不打印密钥值。

## 六、与文章的差异（如实记录）

1. **文章用官方 `examples/chatbot` 验证基线**，本仓库用自己的 `digital-human` 模块验证——
   因为本系列后面十七掌都长在这个模块上，用别人的示例验证不了自己的基线。
2. **文章建议用 SDKMAN 装 JDK 21**，本机直接使用已有的 JDK 21.0.8；enforcer 会把「必须 21」这件事钉住，
   装法不重要，版本一致才重要。
3. **文章提到 Reactor 调试参数 `-Dreactor.trace.operatorStacktrace=true`**，本掌不涉及响应式流，留到真正用到的章节。
4. **踩坑记录**：Windows PowerShell 5.1 按 ANSI 读取无 BOM 的 `.ps1`，中文会被读坏直接导致语法错误。
   本仓库的 `.ps1` 一律保存为 **UTF-8 with BOM**（用编辑器保存时注意别丢 BOM）。
