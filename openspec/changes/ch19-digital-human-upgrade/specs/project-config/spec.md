# Spec Delta

## Purpose

把「一个数字人长什么样、用哪个声音、依据哪些知识、能调用哪些外部能力」变成可配置的数据，
并让「配置」与「已经发布出去的运行实例」分开——运营改配置不应该意外改掉访客正在看到的东西。

## ADDED Requirements

### Requirement: 项目配置的可选项来自预置目录

数字人项目 SHALL 通过从预置目录中选择的方式配置音色、形象与知识库，
MUST NOT 要求调用方提交任意自由文本的供应商标识。

#### Scenario: 查询可选项

- **WHEN** 已登录的企业用户请求数字人配置的可选项
- **THEN** 系统返回音色、形象、模型的可选项清单，每项含稳定标识与展示名

#### Scenario: 提交不在目录中的选项

- **WHEN** 用户提交一个不在预置目录中的音色或形象标识
- **THEN** 系统以明确的校验错误拒绝，且该项目的配置不被修改

### Requirement: 项目可配置能力开关

数字人项目 SHALL 能配置开场白、立场（回答边界与拒答口径）、知识库、MCP 服务与外部 Agent 的启用情况。
未启用某项能力时，运行实例 MUST NOT 调用它。

#### Scenario: 未启用知识库

- **WHEN** 项目的知识库未启用
- **THEN** 该项目的对话不进行知识检索，且回答不声称引用了资料

#### Scenario: 未启用 MCP 服务

- **WHEN** 项目未勾选任何 MCP 服务
- **THEN** 该项目的对话不出现这些 MCP 服务的工具，模型也不被告知它们存在

#### Scenario: 启用外部 Agent

- **WHEN** 项目启用了某个外部 Agent
- **THEN** 该 Agent 出现在可调用范围内，且其不可用时有明确的失败反馈而不是静默跳过

### Requirement: 发布状态机

项目 SHALL 具有「草稿」与「已发布」两种状态。发布动作 MUST 固化一份可复现的配置快照，
发布之后的配置修改 MUST NOT 改变已发布实例的行为，直到再次发布。

#### Scenario: 发布项目

- **WHEN** 用户对一个校验通过的项目执行发布
- **THEN** 项目状态变为已发布
- **AND** 系统记录这次发布所使用的完整配置快照与发布时间

#### Scenario: 发布后修改配置

- **WHEN** 用户在已发布状态下修改音色、开场白或知识库
- **THEN** 已发布的运行实例仍按上一次发布的配置运行
- **AND** 运行入口明确提示「存在未发布改动」

#### Scenario: 重新发布

- **WHEN** 用户再次执行发布
- **THEN** 新的配置快照成为运行实例的依据，旧快照仍可查询

#### Scenario: 配置校验不通过

- **WHEN** 用户对一个引用了不存在音色、或引用了无权访问的知识库的项目执行发布
- **THEN** 发布被拒绝并列出具体原因，项目状态保持为草稿

### Requirement: 所有权隔离

项目的查询、修改、发布 MUST 只对所有者开放。访问他人的项目 MUST 返回「不存在」，
MUST NOT 返回「存在但无权限」，以避免越权探测。

#### Scenario: 访问他人项目

- **WHEN** 用户请求一个属于他人的项目
- **THEN** 系统返回不存在，MUST NOT 泄露该项目的任何字段

#### Scenario: 发布他人项目

- **WHEN** 用户尝试发布一个属于他人的项目
- **THEN** 系统返回不存在，且该项目状态不变

### Requirement: 配置只由所有者修改

数字人项目的配置 MUST 只能通过已登录的企业用户会话修改。
访客侧入口 MUST NOT 提供任何修改项目配置的能力。

#### Scenario: 访客尝试修改配置

- **WHEN** 访客侧入口收到修改项目配置的请求
- **THEN** 请求被拒绝，配置不变
