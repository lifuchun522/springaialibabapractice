# Design

## Context

见 `proposal.md` — Why。设计只需要补充三件现状事实：

1. **三张表已经存在但缺配置位**：`digital_human_project` 有 `status`（`DRAFT` / `PUBLISHED`）与主题色、背景图、开场白、
   结束语；`agent_config` 有 `provider` / `model` / `system_prompt` / 温度 / `max_tokens`。
   **`status` 字段目前没有任何状态机语义**——谁都能直接改成 `PUBLISHED`，也没有「发布快照」的概念。
2. **注册中心的代码已存在且已验证过一半**：`digital-human/.../a2a/AgentRegistrySupport.java`
   已经把「Nacos 优先、本地静态表兜底」写成代码；`knowledge-agent/.../registry/NacosRegistrar.java`
   已经能注册实例。缺的是运行环境（编排里没有 Nacos）、正确的实例地址（现在是硬编码 `127.0.0.1`）与注册结果校验。
3. **模型通道只有一条**（DeepSeek / OpenAI 兼容）。第 15 掌的测试分层已经把
   「mock 边界撤到 HTTP 层」定死，本掌的语音与注册能力必须沿用同一套离线可跑的口径。

## Goals / Non-Goals

**Goals**

- 五个组件在架构图上各有确定位置，且图上能读出「依赖方向」而不只是「有哪些框」。
- Nacos 从「代码里有、环境里没有」变成「跑得起来、查得回来、挂了能降级」。
- 语音能力以可替换的方式接入，且不破坏「离线测试、无密钥可跑」这条仓库基线。
- 发布后的运行实例与草稿配置严格分离。

**Non-Goals（设计层边界）**

- 不引入第二条模型通道。TTS/ASR 是**能力**，不是 `ChatModel` 的兄弟——它们不进 `spring.ai.model.chat` 的选型逻辑。
- 不让 Nacos 承担配置中心职责：不往 Nacos 写业务配置，不读它的配置项。
- 不为实时交互层写任何服务端推理代码（本掌不部署 livekit-server / livekit-agent）。

## Decisions

### D1：架构图按「链路」扩，不按「组件清单」扩

**决定**：`README.md` 的总图从「一条链路加五个框」改为**三条链路**（管理 / 对话 / 注册），
五个组件按所属层入图；另有四张图各自回答一个问题（语音链路、注册中心、运行页数据流、实时交互预留）。

**为什么不用「加框」方案**：把五个框平铺进同一张图，会同时丢掉三个信息——
哪些组件是外部依赖（阿里云）、哪些是自建进程、哪些只是预留。
一张读不出「谁依赖谁、谁是外部」的架构图，会在下一个需求到来时被再次画错。
分链路之后，「加一个能力该落在哪条链路」变成可以照着回答的问题。

**被否方案**：只保留一张大图、用颜色区分层。否掉的理由是 Mermaid 的颜色在图被复制到
文章或 Wiki 后会丢失，而链路分组不会丢。

### D2：livekit-server / livekit-agent 进「实时交互层」但标记为预留

**决定**：两个组件进图，实线变虚线，并标注「本掌不部署，预留位」。

**为什么仍要画**：`docs/ch03-数字人底座.md` 已经把实时链路的结构定死
（「Web ⇄ LiveKit ⇄ Realtime Bridge ⇄ Spring Boot」），第 3 掌的取舍是
**理解与推理收回 Spring Boot，Bridge 只做音频与协议适配**。这个结构决策如果不落在图上，
后面接手的人会重新长出「Bridge 自己直连模型」的第二套工具注册表。
画出来的成本是一行虚线，不画的成本是重复一次第 3 掌的论证。

**代价与缓解**：图上出现「有但不能用」的组件容易误导。缓解方式是虚线 + 图注 + 第五节
「明确不交付」三处同时声明，并且验收记录里如实记账。

### D3：TTS / ASR 走阿里云 NLS，但用适配器隔离

**决定**：调用方只依赖标准语音契约（合成 / 识别），NLS 只出现在一个适配器实现里。
临时凭证由服务端签发，长期密钥只从环境变量进。

**为什么不是「直接用供应商 SDK 调」**：本掌的核心验收点之一是
「换供应商不改调用方」。如果业务代码直接 `new SpeechSynthesizer(...)`，
这条验收项根本无法证明。适配器的成本很小（一个接口 + 一个实现），
换来的是这条验收项可以在测试里用假实现直接证伪。

**为什么不让 NLS 适配器实现成 `ChatModel` 通道**：语音能力是**输入输出模态**，
与「用哪个大模型对话」正交。混进模型选型逻辑会让 `spring.ai.model.*` 的开关语义变得含混，
也会让「模型切换」这个已有能力出现语音副作用。

**被否方案**：直调供应商 REST 端点（依赖最少，但把调用方绑到具体协议，且拿不到流式中间结果）。

### D4：Nacos 用官方镜像 + 复用同一 MySQL 实例，新增 `nacos_config` 库

**决定**：编排里新增一个 Nacos 服务，数据源指向仓库已有的 MySQL 实例，只多一个 database。

**为什么复用而不是新起 MySQL**：本掌的部署形态是「一台机器上的最小闭环」。
多起一个 MySQL 意味着多一份备份、多一套账号、多一处密码轮换；
而 Nacos 的数据量极小（配置表 + 服务表），共用一个实例是这一档规模下的正确取舍。

**代价与缓解**：数据库故障的影响面从「业务表」扩大到「业务表 + 注册表」。
缓解是 Nacos 的**降级路径必须真实可用**：注册中心不可用时，
调用方按本地配置继续工作（这条在 `AgentRegistrySupport` 里已实现，MCP 侧照抄）。

**版本与依赖风险**：Nacos 服务端版本必须与既有 `nacos-client` 2.4.3 同分支，
否则会出现「客户端连上但行为不一致」。具体镜像 tag 与 NLS SDK 坐标在 tasks 第 1 项里
用构建门禁验证后定死，不凭记忆写进文档。

### D5：注册中心登记「位置与清单」，不登记「结构与真值」

**决定**：MCP 服务登记服务标识、协议类型、端点、版本、工具名与摘要；
**工具参数的完整 schema 不搬进注册中心**。

**为什么**：工具 schema 是模型调用契约的一部分，真值必须与实现代码同仓同版本。
一旦 schema 出现第二处真值，就会出现「注册中心写了 3 个参数、代码里已经 4 个」这类
只在运行期暴露的偏差，而且排查时两边都「看起来对」。
这条边界写进 design 而不是只写进文档，是因为它是**下一次改动的护栏**。

### D6：发布 = 固化配置快照，而不是改一个状态字段

**决定**：发布动作写入一份不可变的配置快照；运行入口读快照，不读草稿。
发布后修改草稿不影响运行实例，运行入口提示「存在未发布改动」。

**为什么不能用「状态字段 + 直接读当前配置」**：那样等于没有发布。
运营改一次音色，线上访客的体验立刻变化——这正是发布要消除的风险。
快照的代价是一张表和一个版本号，收益是「线上表现可复现、可回滚」。

**被否方案**：发布时把配置复制进项目表（无版本历史，无法回滚到上一版）。

### D7：形象驱动做成可替换接口，本阶段用前端实现

**决定**：运行页定义「音频输入 → 形象表现」的驱动契约，本阶段实现为前端驱动
（音频播放时按节奏驱动位移/表情贴图），并提供假数据驱动用于离线测试。
真实口型推理明确记为遗留。

**为什么不在运行页里写死前端实现**：如果驱动逻辑直接写进页面，
后续接入真实推理时页面要重写，且「形象驱动」这件事永远无法被单独测试。
接口化之后，验收项「替换驱动实现后页面无需修改」可以被真实证伪。

### D8：开放入口的身份是「项目内的访客」，不是「企业账号」

**决定**：企业账号（注册 / 登录）与访客身份（登记用户名）是**两套命名空间**，
访客身份按项目隔离，只能触及本项目范围。

**为什么**：第 5 条主流程的要求是「登记用户名即可交互」。如果复用企业账号体系，
访客就让账号表承担了两种语义（内部运营 + 外部访客），权限边界会随需求变形。
两套命名空间的代价是两套校验路径，收益是越权探测在入口处就被挡住。

**安全边界**：访客侧不提供任何修改项目配置的能力；
跨项目访问一律拒绝；同一会话的并发对话请求拒绝后到的那次
（沿用既有 `ConversationGuard` 的口径，避免两次回答交叉写入同一条会话）。

### D9：字幕分句与音频的时间对齐

**决定**：字幕按**句**切分并带序号下发；音频按同一分句单元合成，
前端按序号顺序播放并在播放该分句时高亮对应字幕。

**为什么按句而不是按字**：按字对齐要求逐字的强制对齐信息，
而流式合成的可用粒度就是句子边界。按句对齐的代价是「字幕跳变」，
收益是可以在合成与播放之间做流水线（下一句合成时上一句已在播），首句延迟显著更低。

**已知不精确**：音频实际时长与字幕显示时长不严格相等。本掌接受这一误差，
不引入强制对齐模型；前端以音频事件为准推进字幕，不按固定时长计时。

## Risks / Trade-offs

| 风险 | 缓解 |
|------|------|
| NLS SDK 与既有依赖（`httpclient`、`jackson`）版本分叉，被 `dependencyConvergence` 拦下 | 这是门禁**应该**拦下的东西：统一到较高补丁版本，不用 exclude 绕过；把这次的分叉记进验收记录 |
| 注册中心与业务库共用实例，数据库故障同时打死两条链路 | 降级路径必须真实可跑（D4）；验收里包含「Nacos 不可用时对话仍可进行」 |
| NLS 需要真实 AccessKey，CI 无法覆盖 | 语音能力的离线测试全部走假适配器（L1/L2）；真实调用证据只在本机执行并存进 `scripts/evidence-ch19/` |
| 图上的 livekit 虚线被误读为「已经能用」 | 虚线 + 图注 + 非交付清单三处声明；验收记录如实记账 |
| 通话访客用户名被占用时静默复用他人会话 | 规格中已定为显式拒绝；实现时以项目 + 用户名做唯一约束 |
| 字幕与音频时长不严格对齐 | 以音频事件推进字幕（D9）；把「不引入强制对齐」记为已知限制 |

## Migration Plan

**部署步骤**

1. 新增 `nacos_config` 库与 Nacos 表结构（`deploy/init-db.sql`）
2. 起 Nacos（编排新增服务），确认控制台可访问
3. 打开 `knowledge-agent` 的注册开关，确认实例出现在 Nacos 上**且能被查询回来**
4. 打开 `digital-human` 的注册发现开关，验证一次跨服务调用落到 Nacos 上的实例
5. 配置语音密钥，验证一次合成与一次识别
6. 走一遍发布流程：配置 → 校验 → 发布 → 访客入口对话

**回滚策略**（按影响从大到小）

- 注册中心问题 → 关掉两个开关，服务退回本地配置，**不需要回滚镜像**（这条是设计出来的能力，D4）
- 语音问题 → 关掉语音开关，对话退化为纯文本（规格已要求交互不中断）
- 配置快照问题 → 保留快照表和旧版本记录，重新发布上一版快照即可回到旧行为
- 数据库层问题 → 新增的只有 `nacos_config` 库与业务侧新增表，业务旧表未改动

**兼容性**：既有接口的路径与语义不变；新增均为增量接口。
`digital_human_project` 与 `agent_config` 只加列，不加非空无默认值的列，避免旧数据迁移失败。

## Open Questions

以下问题不影响规格、实现路径与任务拆分，可在实现阶段直接定：

1. 访客会话的保留策略（保留多久、是否清理）——本掌沿用既有会话账本表，不单独清理。
2. 形象素材的存放方式（静态资源目录 vs 对象存储）——本掌用静态资源目录，符合「一台机器最小闭环」。
3. 语音合成的语速、音量等细粒度参数是否开放给运营——本掌只开放音色选择，其余用服务端默认值。
